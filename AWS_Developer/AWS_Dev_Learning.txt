   Model - Real-Life Analogy 
   IaaS - You cook everything at home 
   PaaS - You get a pizza base and add your own toppings.

Definition - You rent raw infrastructure - virtual machines, storage, networks - and manage everything else yourself. 

Analogy: Like renting land and utilities - you build your own house (OS,app, etc.) on it.

Definition - You rent a platform - per-configured OS + runtime - to just focus on writing and deploying your app. 

Anaology: Like renting a fully-built house with Kichen, plumbing, etc. - you just bring your furniture (your code)

AWS (Amazon Web Services) Global Infrastructure Overview:

AWS's (Amazon Web Services) global infrastructure is designed to provide:
- High avaliability , Low latency, Fault tolerance, and Disaster recovery 

AWS is built using three main components:

Component -  Think of it as.... - Example 

Region  -  Country/large area - us-east-1(N. Virginia)

Availability Zone (AZ) - Data Center group in a region - us-east-1a, us-east-lb 

Edge Location - Local content delivery - CDN point near users 

1, Regions 
What is it?
A Region is a geographical area that contains 2 or more Availability Zones (AZs).
- Each region in isoloated from others. 

Example Regions: us-ease-1: North Virginia (popular,oldest), ap-south-1: Mumbai, ca-central-1:Canada (Central) , eu-west-1: Ireland 

Developer Use: Choose a region near yours users for low latency: 

aws configure --region ap-south-1 
// is used to setup or update AWS CLI configuration, specifically the region for your AWS operations.
// aws configure - This command launches an interaction setup wizard to configure the AWS CLI with Access Key ID, Secret Access Key, Default region, Output format 
// --region ap-south-1: This flag overrides the default region only for this command i.e., the region ap-south-1 (Mumbai) is used only during this configuration session.

2, Availability Zones (AZs)

- Each region has 2 to 6 AZs (most have 3+)
- An AZ = one or more isolated data centers with: independent power, separate networking, Physical distance from other AZs ( for fault tolerance)

Why AZs?

- High availability: If one AZ fails, others are still up.
- Disaster recovery: Spread services across AZs.

Best pratics: Deploy across multipler AZs.

3, Edge Locations 
- These are content delivery endpoints used by AmazonCloudFront (CDN).
- Located in hundreds of cities worldwide.
- Purpose: Cache data closer to users -> faster websites, videos, apps.

Think Netflix: Content is streamed from nearest edge, not central data center.

Bonus concepts:

Local Zones:
- Extend AWS services to major cities closer to users (e.g., for gaming, live streaming).
- Lower Latency than a region 

WaveLength Zones:
- Used for 5G applications -> ultra-low latency on mobile networks.

AWS Outposts:
- Run AWS services on-premises(your own data center), but managed by AWS. 

How does AWS ensure high availability?

A, AWS uses regions with multiple availability Zones. you can deploy your applications across AZs so that even if one fails,
   other continue serving users. Edge Locations help serve content faster by caching it near users globally.

IAM Groups: 

Why Use IAM (Identity and Access Management)  Groups?
- Instead of assigning permissions one by one to each user (which is painful), you:
  - Create a group (e.g., Developers, Admins) 
  - Attach policies (permissions) to that group 
  - Add users to that group 
  
Benefits:
- Simplifies management
- Ensure consistency 
- Easier auditing & updates 

Example Scenario:

Let's say you have 3 developers:

- Alice, Bob, Charile

2, Attach an S3 (simple storage service) ReadOnly policy to the group.
3, Add Alice, Bob, Charlie to that group 

- Now they all have s3 (simple storage service) read access!

6, Add users to the group 
7, Done!

What is an IAM Role?

- An IAM Role is like a temporary identity with specific permissions that any trusted entity
  (user,app,service,EC2(Elastic Cloud compute) ,Lamdba,another AWS (Amazon web services) account) can assume to perform actions. 
  
- Think of a role as a "uniform" - when someone wear it, they get the authority (permissions) that come with it. 

Why Use Roles?

- Grant temporary permissions.
- Avoid long-term access keys or passwords.
- Allow services like EC2 (Elastic compute cloud) , Lamdba to securely call other AWS (Amzaon Web Services) services.
- Enable cross-account access securely. 

Common Use Cases:

Use Case - Description 

EC2 (Elastic compute cloud)  instance to S3 (simple storage service) - An EC2 (Elastic compute cloud) instance writes logs to S3 (simple storage service) using a role 

Lamdba to DynamoDB - Lambda function reads/writes data in DynamoDB via a role 

Cross-account access - User in Account A accesses resources in Account B by assuming a role 

Federated login - Login via Google, Facebook etc, and assume a role in AWS ( Amazon Web Services)  

IAM (Identity and access management) Role Components: 
1, Trust Policy (Who can assume the role?)
2, Permissions Policy (What can the role do?) 

Trust Policy (Who can assume the role?) 

Here's a basic trust policy that lets EC2 (Elastic compute cloud) assume the role:

{
"Version":"2012-10-17",
"Statement":[{
"Effect":"Allow",
"principal":{
  "Service":"ec2.amazonaws.com"
},
"Action":"sts:AssumeRole" 
}]
}

sts:AssumeRole means "I want to put on the uniform(role)." 

Permissions Policy (What can the role do?)
- Attach policies just like a user/group. Example: S3 (Simple Storage Service) ReadOnly 

{ 
"Version":"2012-10-17",
"Statement":[{
"Effect":"Allow",
"Action":"["s3.GetObect","s3:ListBucket"],
"Resource":"*"
}]
}

Example Scenario: EC2 (Elastic compute cloud) Role to Access S3 (simple storage service) 

1, Create IAM (Identity and access management) role 
      - Trusted entity: EC2 (Elastic Compute Cloud) 
	  - Permissions: S3 read access (Simple Storage Service) 
	  
2, Attach role to EC2 (Elastic cloud compute) instance 
3, EC2 (Elastic compute cloud) instance now has access to S3 (simple storage service) without keys.

IAM (Identity and Access management)  best practices in Cloud:

1, Principle of Least Privilege (PoLP)
- Only give the minimum permissions needed to do the job 

. Use fine-grained IAM policies 
. Avoid using * in Action or Resource 
. Regularly audit permissions 

Example (AWS IAS Policy):

{
"Effect": "Allow",
"Action": "s3:GetObject",
"Resource": "arn:aws:s3::my-bucket/*"
}

2, Use Roles Instead of Users 
-  Assign IAM roles to applications, instances, containers - not IAM users.
. Use IAM roles for EC2, Lambda, EKS, etc. 
. Use federated access (e.g., SSO via Okta, AD) for users 

3, Enable MFA (Multi-Factor Authentication) 
- Require MFA for all privileged accounts and users.
. Use virtual MFA (like Google Authenticator) or hardware tokens 
. Especially critical for root/admin accounts. 

4, Group Users with Roles or Permissions 
- Manage users via groups, not individual policies.
. Example :
  1, Developers group -> Read/write to Dev resources.
  2, QA group -> Read-only to Production resources 
  
5. Monitor and Audit with cloud logging 
- Use audit logs to track who accessed what and when.
. AWS: Enable CloudTrail, Access Analyzer, and Config 
. Azure: Use Azure Monitor, Activity Logs 
. GCP : Use Cloud Audit Logs 

6. Use Temporary Credentials (STS tokens) 
- Avoid long-lived credentials or static access type.
. USe AWS STS, Azure AD tokens, or GCP short-lived OAuth tokens.
- Auto-rotate and expire credentials.

7, Never Hardcode Secrets 
Never store IAM keys, passwords, or tokens in code or Git. 
- Use secret managers:
. AWS Secrets Manager 
. Azure Key vault 
. GCP Secret Manager 

8, Apply Resource-Level Permissions:
Don't just assign service-level access. Use resource-level scoping.

Example: Allow read access only to a specific S3 bucket, not all buckets. 

9, Regularly Review and Rotate Access:

Periodically: 
1, Audit who has access.
2, Remove unused accounts/roles.
3, Rotote IAM keys and credentials

10. Use IAM Policy Simulator or Access Analyzer 
- Test policies before applying them. 
. AWS: IAM policy simulator 
. Azure: Use What-If tool in role assignments
. GCP : Use policy Troubleshooter

IAM Roles for AWS Services 

What is an IAM Role?
- An IAM role is an AWS identity with specific permission that can be assumed by AWS services, applications, or users.

. Unlike users, roles don't have long-term credentials (username/password or access keys).
. Roles are used by AWS services like EC2, Lambda, ECS, etc. to perform actions on your behalf.
 
Why are Roles Important on the Exam?
- They help you:
. Grant access safely and temporarily.
. Avoid using static access keys in your app.
. Follow the principle of least privilege 

Common Use Cases on the AWS Developer Exam:

Service - Role Use Case 
EC2 - Instance needs to call S3,DynamoDB, etc.
Lambda - Lambda function needs to call other AWS services.
ECS Tasks - Containerized app needs permissions to access other AWS resources. 
CodeBuild - Needs to access GitHub, S3 artifacts, or deploy 
Step Function - Needs to invoke Lambda or other services 
API Gateway + Cognito - Assume IAM role to access backend securely

Example: IAM Role for Lambda Function 
1, Create IAM Role with trust policy for Lambda:
{
 "Version":"2012-10-17",
 "Statement": [{ 
    "Effect":"Allow",
    "Principal":{
       "Service":"lambda.amazonaws.con"
	 },
    "Action": "sts:AssumeRole" 	 
 }]
} 

2, Attach policy to allow access to S3 
{
  "Effect":"Allow",
  "Action":["s3:GetObject","s3:PutObject"],
  "Resource": "arn:aws:s3::my-bucket/*" 
}

3, Assign role to Lambda during creation or update 

Trust Relationship:

- IAM roles are assumed by AWS services. 
- The trust policy defines who can assume the role. 

Common trusted entities: 
. "Service":"lambda.amazonaws.com" 
. "Service":"ec2.aamzonaws.com"
. "Service":"ecs-tasks.amazonaws.com" 

Spot Wrong Access Scenarios: 

- x - Lambda function using hardcoded credentials instead of a role. 
- x - EC2 instance needs S3 access but no IAM role is attached.
- x - Role assigned to user instead of service 

- Always choose IAM roles over access keys for services. 


How Temporary Credentials Work:
- When a service assumes a role, AWS uses STS (Security Token Service) to provide:
1, Access key ID
2, Secret Access Key 
3, Session Token (valid for a short period)
These are rotated and managed automatically for the service.

IAM Role - Temporary credentials for AWS services

What Happens When you Stop an EC2 instance? 
1. Definition
- Stop = Shutdown the instance (like powering off a physcial computer) but keep the EBS volume and settings.
- Instance can be restarted later. 

2. Key Effects 
Feature - Behaviour when stopped 

EBS Volumes - Remain attached and data is retained (unless you manually detach or delete)
Instance Store - Data is lost (because it's temporary) 
Public IP4 - Lost if it was auto-assiged (ephemeral). Keep it only if you use Elastic IP.
Privat IP4 - Remains the same. 
Billing - EC2 compute charges stop; EBS storage charges continue. 
Elastic IP - No extra cost if attached to running instance, but charges apply if stopped. 
RAM/Processes - Lost - nothing runs while stopped. 

3. Technical Details 
- Instance state changes :  running -> stopping -> stopped. 
- You can change instance type when stopped.
- you can modify EBS volumes when stopped.
- you can move to another Availaibility Zone only by creating an AMI and launching a new instance. 

4. Stop vs Terminate 

Action: Stop 
EBS Data: Preserved 
Instance Store Data: Lost 
Instance Availability: Can restart 

Action: Terminate 
EBS Data: Deleted if "Delete on Termination" enabled 
Instance Store Data : Lost 
Instance Availability : Cannot restart 

5, Common Exam Traps 
1, Willing stopping EC2 keep public IP? 
   -> No, unless using Elastic IP4
 
2, Does stopping incur charges?
   -> No compute charges, but still pay for EBS 
   
3, Can you restart EC2 with same private IP?
   -> Yes, same private IP within Same VPC 
   
6, Real Example 
If you have 
- 1 EC2 instance with t2.micro (on-demand)
- 8 GB gp3 EBS volume 

Running for 30 days - Charged for compute + storage 
Stopped for 30 days - Charged only for EBS storage.

What is Ec2 Hibernate?
- Hibernate = Save the RAM state of the instance to disk, then shut it down. 
- When restarted, it resumes from RAM snapshot (like putting a laptop into sleep mode)
- Saves time compared to a full reboot or stop/start.

What happens in Hibernate 

Resource - Behaviour 

RAM - Saved to the root EBS volume (must be encrupted). Restored on restart. 
Instance ID - Same after resume.
Private IPV4 - Remains the same 
Public IPv4 - Lost if auto-assigned, retained if using Elastic IP.
Elastic IP - still attached 
EBS Volumes - Data Persists (RAM image stored in root volume)
Instance Store - Data lost (not preserved)
Billing - Compute charges stop, storage charges continues (EBS + RAM snapshot).

Requirements for Hibernate:
1, Instance type must support hibernation (most general-purpose + some memory-optimized).
2, Root volume must be EBS, encrupted, and large enough to hold RAM contents.
3, Instance RAM size <= 150 GB.
4, Available only for On-Demand and Reserved instacnes (not Spot).
5, Suppose OS: Amazon Linux 2, Ubuntu, Windows (some versions)

Key Differences: Stop vs Hibernate 

Action: Stop
RAM : Lost 
Public IP: Lost (unless Elastic IP)
Instance Store: Lost 
Restart Speed: Cold boot (OS + apps restart)

Action: Hibernate
RAM : Perserved (saved to EBS)
Public IP : Lost (unlese Elastic IP)
Instance Store : Lost 
Restart Speed: Fast boot (resumes apps)

Commont Exam Traps:
1, Does Hibernate save processes?
- Yes, because RAM contents are saved.

2, Can I hibernate Spot instance?
- No, only on-Demand and Reserved. 

3, Do I pay while hibernated?
- No compute charges, EBS storage charges.

4, What if RAM > 150 GB?
- No supported 

- Exam Keyword to Remember:
  Hibernate = Stop + Save RAM 
  Best for long-running apps that need to resume quickly.

Amazon EC2 Security Group 

1, What is a Security Group?
A, 
- A virtual firewall that controls inbound and outbound traffic to your EC2 instances.
- Applied at the instance level (not subnet level -> that's NACL)
- Works only for IPv4, IPv6, and port-based rules. 

2. Key Properties 
Property - Explanation
1, Stateful - if inbound traffic is allowed , the response is automatically allowed (no need to add outbound rule).
2, Default Rules - By default -> All inbound traffic denied, All outbound traffic allowed.
3, Instance Association - Can attach multiple security groups to 1 EC2.
4, Rule limits - Each Security Group can have up to 60 inbound + 60 outbound rules (soft limit,exam may test)
5, Region/VPC Scoped - Security Groups exist inside a VPC, not globally. 

3, Rule Types 
- Rules are allow only (no deny rules - unlie NACLs) 
- you define:
         - Protocol (TCP, UDP, ICMP, etc.)
		 - Port Range(e.g, 22 for SSH, 80 for HTTP, 443 for HTTPS)
		 - Source (CIDR block, another Security Group or IP range) 
		 
4, Common examples 
Use Case  - Inbound Rule 

1, Linux SSH - Allow TCP 22 from your IP.
2, Windows RDP - Allow TCP 3389 from your IP 
3, Web Server = Allow TCP 80 (HTTP) + 443 (HTTPS) from 0.0.0.0/0 
4, App Server = Allow TCP 3306 (MySQL) from APP Server's security Group 

5, Security Groups vs NACLs (Exam Favorite)

Feature : Level
Security Groups : Instance-level 
NACLs - Subnet-level 

Feature : Rules 
Security Gruups: Allow only 
NACLs - Allow + Deny 

Feature : Stateful 
Security Group : Yes 
NACLs : No (stateless, need inbound + outbound rules)

Feature : Default  
Security Group : All inbound denied, all outbound allowed. 
NACLs : All inbound/outbound allowed  

Feature : Typical Use 
Security Group : Control access to EC2 
NACLs : Control subnet traffic 

6, Developers Exam Pitfalls
1, can you block an IP in security Group?
A, No, use NACL for denies 

2, Do Security Groups affect outbound traffic?
A, Yes, but by default all outbound is allowed. 

3, Can I attach 1 EC2 to multiple Security Groups?
A, Yes, Rules are unioned. 

4, Do Changes apply immediately?
A, Yes, changes are live, no reboot required.

5, What is default inbound?
A, All traffic denied until you add rules.

Exam Keywords:
- Stateful firewall, allow-only, instance-level, live changes, inbound denied by default, outbound allowed by default.

Amazon EC2 User Data Scripts

Amazon EC2 Key Pairs 

1, What is a Key Pair?
A, 
- A Key Pair = Public Key + Private Key used to securely connect (SSH) to Linux EC2 instances (or RDP for Windows)
- AWS stores the public key; you download the private key (.pem) when creating the pair.
- Without the private key, you cannot SSH into EC2 (unless you create a new one and update). 

2. How it works 
1, You create/download a Key Pair in AWS 
2, AWS injects  the public key into the EC2 instance at launch (into ~/.ssh/authorized_keys file).
3, you connect using the private key:
   ssh -i mykey.pem ec2-user@<Public-IP> 
4, The instance authenticates you by matching your private key with its stored public key. 

3, Key Pair Formats 
- PEM (.pem) -> Used by Linux & Mac for SSH.
- PPK (.ppk) -> Used by PuTTY(Windows) 
- Exam Tip : AWS gives you only one chance to download the private key file (.pem) when creating a key pair.
  If you lost it -> you cannot download again. 
  
4, Where to Create Key Pairs 
   - AWS Console -> EC2 -> Key Pairs -> Create Key Pair.
   - AWS CLI:
     aws ec2 create-key-pair --key-name MyKey --query 'KeyMaterial' --output text > MyKey.pm 
	 - Must set correct permissions:
	   chmod 400 MyKey.pm 
	   
5, Connecting to Linux EC2 
   ssh -i MyKey.pem ec2-user@<Public-IP>
   - Default usernames:
     - Amazon Linux -> ec2-user 
     - Ubuntu -> ubuntu 
     - RHEL -> ec2-user or root 
     - CentOS -> centos 

6, KeyPair and Windows EC2 
   - For Windows instances, key pairs are used to decrupt the Administrator password.
   Steps:
   1, Launch Windows EC2 with Key Pair.
   2, Get Administrator password via Console -> Decrypt with .pem key.
   3, Connect using RDP with username Administrator 

7, Exam Traps 
1, What if lost the .pem file?
A, You cannot download again. You must create a new key Pair and update the instance's ~/.ssh/authorized_keys    

2, Can I reuse a Key Pair across instances?
A, Yes 

3, Can multiple instances share one key pair?
A, Yes, but not recommended for security.

4, Are Key Pairs global?
A, No, Key Pairs are Region-Specific 

5, Where is the public key stored?
A, On the EC2 instance, inside ~/.ssh/authorized_keys 

Exam KeyWords: SSH, PEM file, root login, injected at launch, region-specific, can't re-downloaded, private key, Windows password decruption

Amazon EC2 Elastic IP 

1, What is an Elastic IP (EIP)?
A, 
- A static, public IPv4 address that you allocate to your AWS account.
- You can attach/detach it to/from an EC2 instance as needed.
- Unlike auto-assigned public IPs, Elastic IPs do not change when you stop/start the instance. 

2, Why Use Elastic IP?
A,
- By default, EC2 instances in a public subnet get an auto-assigned public IPv4.
  - This changes every time you stop/start the instance.
- Elastic IP solves this:
  - Keeps the same IP address even after reboots or stop/start cycles.
  - Useful for stable DNS mappings, production apps, or whitelisted IPs. 
  
3, Key Properities 
Feature - Behaviour 
1, Static - The IP does not change unless you release it. 
2, Region-specific - You can only use it in the Region where it was allocated.
3, Limit - By default, 5 Elastic IPs per Region (soft limit). 
4, Free vs Charged - Free if attached to a running instance. AWS charges if allocated but not used.
5, Re-assignment - you can remap it from one EC2 to another intantly (useful in failover) 

4, Typical Workflow 
1, Allocate an Elastic IP in AWS Console or CLI:
   aws ec2 allocate-address 
2, Associate it with an instance:
   aws ec2 associate-address --instance-id i-1234564679adfadf --allocation-id eipalloc-123456789 
3, If needed, reassign to another instance 
   aws ec2 disassociate-address --association-id eipassoc-12345678
   aws ec2 associate-address --instance-id i-abcdef123456479 -allocation-id eipalloc-123456789 

5, Exam Traps:
1, What happens to auto-assigned Public IP if instance stops/starts?
A, It changes. Only Elastic IP stays the same.

2, Are Elastic IPs free?
A, Free if attached to a running instance. 
   Charged if allocated but not attached. 
   
3, Can Elastic IPs be moved across Regions?
A, No, Region-specific 

4, Can mutliple instances share one Elastic IP?
A, No, 1:1 mapping at a time, but you can remap quickly.

5, Do Elastic IPs work with IPv6?
A, No, Elastic IPs are IPv4 only.

6, Real-world Use Case 
- you run a web app EC2 instance and map myapp.com -> IP address 
- If you use the auto-assigned IP, every reboot changes the address -> downtime 
- With an Elastic IP, the IP stays the same -> no DNS updates needed. 

Exam Keywords:  Static IPv, Region=specific, free only if in use, survives stop/start, remap for failiver, IPv4Only.

Amazon EC2 Network ACLs (NACLs) : 

1, What is a NACL?
A,
- Network Access Control List (NACL) = Firewall at the subnet level.
- Controls inbound and outbound traffic for all resources inside a subnet.
= Think of it a security filter around the subnet, while security Groups filter traffic at the instance level. 

2, Key Properties 

Feature - NACL 

Scope - Works at subnet level (applies to all instances in that subnet)

Stateless - Responses to allowed traffic are not automatically allowed. you must define rules for both inbound and outbound. 

Rules - Numbered (lowest number has priority) 

Default - Default VPC has a default NACL that allows all inbound/outbound traffic. 

Custom - Custom NACLs start with deny all (block everying) until rules are added. 

Explicit Deny - Supported (unlike Security Groups) 

Rule Action - Allow or Deny 

3, Rule Evaluation 

- Each NACL's rule has:
     - Rule Number ( processed in order: lowest -> highest)
     - Protocal ( TCP, UDP, ICMP, etc)
     - Port range 
     - Source/Destinction CIDR 
     - ALLOW / DENY 
- The first matching rules wins, rest are ignored. 
- if no rule matches -> traffic is denied. 

Example:

Image an inbound NACL with rules:

Rule#  -   Type  - Source  - Action 
100 -  SSH(22) - 0.0.0.0/0  -  ALLOW 
110 - HTTP(80) - 0.0.0.0/0  - ALLOW 
* - ALL - ALL - DENY 

5, NACL vs Security Group  

Feature -  Security Group - NACL 
Scope - Instance-level - Subnet level 

Stateful? - Yes (return traffic auto allowed) - No(must allow return explicitly) 

Rules - Only Allow - ALLOW + DENY 

Default - All rules applied - Rules evaluated by order ( lowest -> highest) 

Use Case - Fine-grained control per instance - Broad control at subnet boundary 

Exam Tip :
- if they ask: "You want to block an IP range from accessing an entire subnet?"  - NACL 
- if they ask: "You wan to allow inbound traffic only to one instance? " -> Security Group 

6. Examp Traps 

1. Stateless nature -> Always mention both inbound + outbound rules.
2, Order matters -> Rule numbers processed lowest first 
3, Explcit Deny Supported (SGs don't support it)
4, Default vs Custom NACL 
   - Default NACL -> Allows everything 
   - Custom NACL -> Denies everything until you add rules.
5, One subnet -> One NACL (but can re-associate) 


Keywords for Exam:
- Subnet level firewall, stateless, ordered rules, ALLOW + DENY, explicit deny, both inbound and outbound required.

Amazon EC2 Elastic Network Interface (ENI) - 

1, What is an ENI?
A, 
- An Elastic Network interface (ENI) is a virtual network card that you can attach to an EC2 instance.
- Every EC2 instance mut have at least one primary ENI to communicate in the VPC.
- You can also create and attach additional ENIs for advanced networking setups.

2, What is inside an ENI?
A, 
- An ENI can include:
  - Primary private IPv4 (required)
  - One or more secondary privates IPv4s.
  - One Elastic IP (EIP) per private IPv4.
  - One public IPv4 (if auto-assigned)
  - One or more IPv6 addresses.
  - Security Groups (like a virtual firewall).
  - MAC address 
  
3, Types of ENIs 

1, Primary ENI 
   - Automatically created when an instance launches.
   - Cannot be detached.
   - stays with the instance until termination. 
   
2, Secondary ENIs 
   - Manually created and attached/detached.
   - Can be moved between instances in the same AZ. 
   

4. Use Cases (Exam Focus)
  - High availability -> Move ENI from one instance to another during failover.
  - Dual-home instances -> One ENI in a public subnet + one in a private subnet.
  - Separate management network -> One ENI for app traffic, aonther for admin/monitoring. 
  - BYO MAC address licensing -> ENIs have fixed MACs, useful for software licenses tied to MAC. 
  
5, Life Cycle:
  - Attach ENI to an instance (hot attach/detach for secondary ENIs).
  - Detach ENI from an instance (while instance is running or stopped).
  - Delete ENI (if no longer needed) 
  
6, ENI vs. Public/Private IP 

Feature - ENI - Public/Private IP 

Scope - Virtual NIC (network card)  - Address bound to ENI 

Move between instances -  Yes (secondary ENIs) - No, tied to ENI 

Has Security groups -  Yes -  No (IP only)

MAC address  - Unique per ENI -  not applicable 

7. Exam Traps 

1, Each ENI belongs to one subnet (one AZ only) -> can't span multiple AZs 
2, Primary ENI cannot be detached, only secondary ENIs can.
3, ENIs survive instance stop/start (they keep their IPs)
4, Secondary ENIs can be hot-attached/detached.
5, Security groups are attached to ENIs, not directly to instances.

Keywords for Exam:

- Virtual NIC, subnet-level, attach/detach, primary vs secondary, hot attach, move across instances in same AZ,
- Security groups bound to ENI, fixed MAC address.

******************************************************************************************************************************

1, Private IP 
- Assigned from the VPC subnet range (e.g., 10.0.0.0/16)
- Used for internal communication between resources inside the VPC.
- Not routable on the internet.
- Persists with the ENI (Elastic Network Interface)
- Every instance must have at least one private IP.
- You can add secondary private IPs to the same ENI.

Example: EC2 in private subnet -> 10.0.1.25 (oly reachable within VPC or via VPN/Direct Connect)

2, Public IP 
- Mapped 1:1 to a private IP using NAT (Network Address Translation)
- Used for internet communincation
- Auto assigned if the subnet setting "Auto-assigned Public IPv4" is enabled.
- Dynamic :
    - if you stop/start the instnace -> public IP changes.
	- if you need a premanent IP, use an Elastic IP 
- Always paired with a private IP on the ENI 

Example:
EC2 in public subnet -> 52.95.124.3 (mapped to private IP 10.0.1.25) 

3, How they work together?
Public IP <-> Private IP binding via the Internet GateWay (IGW)
Inside VPC -> Other instances use private IP 
Outside (interent) ->  Use public IP / Elastic IP 

4, Exam Tip - Elastic IP 

- An Elastic IP (EIP) -> static public IP.
- Attached to a private IP on an ENI.
- Does not change if the instance is stopped/startd. 
- Use case: Long-lived servers that need a fixed public address. 


5, Key Differences 
Feature  -   Private IP -  Public IP 
Scope - Internal (VPC only) - Internet 

Default - Always assigned  - Optional (subnet setting) 

Persistance -  Persists with ENI - Changes on Stop/start (unless Elastic IP)

Communincation - Instance <-> Instance in VPC  - Instance <-> Internet 

Elastic Option -  Secondary private IPs - Elastic IP (static) 


Exam Traps:
1, Public IP is always mapped to a private IP.
2, Public IP changes when instance is stopped/started (unless EIP).
3, Elastic IPs are the only way to keep a fixed public IP.
4, Inside VPC, instances always talk to each other using private IPs, even if they also have public IPs.

What is AWS Lambda?
- Serverless compute service in AWS.
- Runs code without provisioning or managing servers.
- You upload your code, configure triggers, and lambda executes it.
- Pay only for the compute time your code consumes (per request + per GB second).

2, Key Lamba concepts (Exam Focus)
- Event driven -> Lamba is invoked by events (API Gateway, S3, DynamoDB, SNS, SQS, etc.).
- Runtime support -> Python, Node.js, Java, C#, Go, Ruby, custom runtime(via container images).

a, Memory & Timeout 
- You configure memory (128 MB - 10 GB) , timeout (max 15 minutes).

b, Scaling -> Auto scales based on number of events.Each request runs in its won isolated environment. 
   
c, Concurrency ->
     . Default concurrency = 1000 per account (can request increase).
	 . Reserved concurrency = guarantees capacity for critical functions.
d, Cold start vs Warm start:
   Cold Start - First invocation takes longer due to container initialization.
   Warm Start - Subsequent requests resue container -> faster 
   
e. IAM role: Each lambad function has an exeuction role defining what AWS resources it can access.

3. Pricing 
- Requests: First 1M request/month free, then $0.20 per 1M requests.
- Duration: Charged per GB second (memory x execution time)
- Example: Function uses 512 MB and runs for 1 sec -> billed as 0.5 GB-second. 

4, Common Lambda Triggers:

a, API Gateway -> Run Lambda as backend for REST/HTTP APIs.
b, S3 Events -> Process files when uploaded/modified.
c, DynamoDB Streams -> React to database changes.  
d, SNS/SQS -> Consume message from queues or topics.
e, EventBridge (ClouldWatch Events) -> Scheduled tasks (e.g., cron jobs)

5, Deployment & Management 

- Package size limit:
  . 50 MB (direct zip uload).
  . 250 MB (when deployed from S3).
  
- Environment variables -> Store config without hardcoding. 

- Versions & Aliases:
  . Version = immutable snapshot of function code/config.
  . Alias = pointer to a version (useful for prod/test traffic shifting).
  
6, Exam Tips & Gotchas 
1. choose Lambda when:
   - You need event-driven, short-running tasks.

2. Not suitable when:
   - Long-running processes (max 15 min timeout).

AWS Lamdba Event Source: DynamoDB Streams

1, what is dynamoDB streams?
- DynamoDB Streams captures a time-ordered sequence of item-level changes (insert, update, delete) in a DynamoDB table.
- Each stream record shows what happened and optionally before-and-after images of the changed item.
- Stream data can automatically trigger a Lambda function.
Think of it like: "A change log for DynamoDB".

2, How it works

App -> writes data -> DynamoDB table 
           |
	   DynamoDB streams records the change 
	       |
	   AWS Lambda polls the stream (asynchronously)
	       |
	   Lambda processes the record (insert/update/delete)
	   
	   
3, Stream View Types 

StreamViewType    -     What It captures   -   Example 
KEYS_ONLY               Only primary key attribute         {"id": 101}
NEW_IMAGE               Entire item after change           updated record 
OLD_IMAGE               Entire item before change          Deleted record 
NEW_AND_OLD_IMAGES      Both old and new                   Before & after snapshot 

Exam Tip: Choose NEW_AND_OLD_IMAGES if you need to compare before vs after values.

4, Lambda Integration Setup 

Step 1 : Enable Streams
    - Go to DynamoDB table -> Exports and streams tab
	- Enable DynamoDB stream.
	- Choose a StreamViewType 
	
Step 2 : Create Lambda Function 
     - Add an event source mapping -> DynamoDB Stream ARN.
	 - Lambda starts polling the stream for new records.
	 
Step 3 : IAM Permissions 
     - Lambda's execution role needs:
	   {
	      "Effect": "Allow",
		  "Action": [
		    "dynamoDB:DescribeStream",
			"dynamoDB:GetRecords",
			"dynamoDB:GetSharedIterator",
			"dynamodb:ListStreams"
		  ],
		  "Resource":"*"
	   }

5, Example Lambda Function 

import json 
def lambda_handler(event, context):
    for record in event['Records']:
        event_name = record['eventName']  # INSERT, MODIFY, REMOVE 
        new_image = record['dynamodb'].get('NewImage',{})
        old_image = record['dynamodb'].get('OldImage',{})

        print(f"Event: {event_name}")
        print(f"New Image: {new_image})
        print(f"Old Image: {old_image})
    return {"StatusCode": 200}

6, Invocation Type 
- DynamoDB Streams -> Lamdba = Poll-based (synchronous)
- Lamdba polls the stream automatically (AWS manages the polling).
- Lambda processes batches of records from the stream.
Exam Keyword: Poll-based stream event source.

7, Important Configurations
Setting - Description 
Batch size - Number of records Lambda reads per batch(1-1000).
Parallelism - One Lambda per stream shard (can process in parallel.)
Retry behaviour - If Lambda falls, AWS retries until successful (no data loss).
Event order - Guaranteed within the same shard.

8, Common Use Cases 
- Real-time analytics - capture data changes immediately.
- Audit logging - store before/after snapshot in S3.
- Cross-table sync - replicate DynamoDB updates to another table.
- Notfications - trigger SNS or SQS from Lamdba when changes occur.

9, Common Exam Types 
- "DynamoDB pushes events to Lambda" - False - Lambda polls the stream.
- "Lambda triggers immediately when an item changes." -  Not instantly - near real-time(polled).
- "Stream records deleted after read." - True - streams are kept for 24 hours max.
- Lambda can lose data if it fails. - False - AWS retries until processed successfully.
- Ordering is always preserved - True - Within the same shard.

10, Exam Keywords to Memorize 
- Poll-based event source - Lambda polls DynamoDB Streams.
- Batch Processing - Multiple records per invoke.
- Shard iterator - Used internally to read stream records.
- 24-hour retention - Streams available for 24 hours.
- StreamViewType - Controls what data appears in stream.
- Ordered processing per shard -  Always preserved.

11, Quick Recap Summary 
TriggerType - Pollbased (managed by AWS)
Delvery Type - Synchronous batch
Data Retention - 24 hours 
Order Guarantee - yes, per shard 
Failure Handling - Retries automatically 
Use Cases - Real-time sync, auditing, analytics
View Options - KEYS_ONLY, NEW_IMAGE, OLD_IMAGE, NEW_AND_OLD_IMAGES
