Do not allow the pipeline to resume if the controller restarts 

What is Jenkins Controller?
- Think of Jenkins as a brain + hands system:
  1) The Controller = The brain (decides what to do, manage jobs).
  2) The Agents (or Nodes) = The hands (actually do the work: build, test, deploy). 
  
Jenkins Controller = The Master (old name)
- Runs the main jenkins service.
- Provides the Web UI(the dashboard you log into).
- Stores job configuration, plugins, build history, credentials.
- Assigns tasks to agents/nodes 
- Can also execute jobs itself (if no agents are configured) -> but not recommeded for large setups.

Responsibiliites of Controller:
1, Manage the UI & Configurations -> You create jobs here.
2, Schedule Builds -> Decides when pipeline or job should start.
3, Distribute works -> sends builds to agent.
4, Monitor & Report -> collects results from agents and shows status green or red. 

Jenkins Agent/Node :
- Separate machine (VM, container, or physical server).
- Executes jobs (compilation, testing, deployments).
- Communicates back with the controller.

Real-World Analogy:
- Controller = Uber App (manages rides, payments, dispatching).
- Agents = Uber Drivers (actually do the driving) 

If the Ubser app(controller) didn't exist, drivers wouldn't know where to go.
If drivers (agents) didn't exist, the app(controller) couldn't complete rides.

Real-Time Example in Companies:

- A game company (like yours) runs Jenkins Controller on a server. 
- Developers push code -> Controller triggers pipelines.
- Heavy builds (Unity/Unreal compiles, automated tests) are sent to powerful build agents with GPUs/CPUs.
- Controller just coordinates; agents do the hard work.


What does it do?

When this option is checked: 
- if the Jenkins controller (master) restarts (e.g., due to server reboot, upgrade, crash), any runnning pipeline will be aborted and not resumed after the restart.

If this option is unchecked (default behaviour): Jenkins will try to resume the pipeline from the last saved stage after a restart - provided the pipeline supports resumption.

Use Cases - When to CHECK this box 

Scenario - Why to Disable Resume 
Critical deployment or destructive tasks - You don't want it to resume halfway through and possibly corrupt production.
Pipelines using non-resumable steps - e.g,. input, docker, or tools that can't be resumed 
Better control over restarts - you want to manually re-trigger the pipeline after a safe restart.
You want a clean slate after restart - Especially in development or debugging environments 

When to LEAVE IT UNCHECKED (default behaviour)

Scenerio - why to Allow Resume 
Long-running test or build pipelines - Prevents wasting hours of progress due to a restart 
Infrastructure-as-code tasks - Resume Terraform/Ansible pipelines form last step 
Building large artifacts - Avoid rebuilding from scratch after restart 
Cloud-based build agents - Controller may restart due to scaling or updates; resuming helps continuity 

Real-World Example:

pipeline {
   agent any 
   options {
     disableResume() // This disables resuming the pipeline 
   }
   stages {
      stage('Deploy') {
	     steps {
		    echo 'Deploying critical system...'
			// Any failure/resume here is dangerous. 
		 }
	  }
   }
}

How It works Internally:

- Jenkins pipelines are built on Durable Task plugin.
- It saves pipeline state between stages or steps using checkpoints.
- if resume is disabled, that state is discarded on controller restart.

Summary:

Option - Behaviour 
Checked - Jenkins will abort the pipeline if controller restarts. 
UnChecked - Jenkins will try to resume the pipeline from the last saved step.

Pipeline -> Advanced Options -> Pipeline Speed/Durability Override 

What Does it control?
- This setting determines how often Jenkins saves (persists) the state of the pipeline to disk while it is running. 

Available Options:

Option - Description - Use Case 

None (use default) - Uses the global Jenkins setting - Let Jenkins decide 

Performance-Optimized - Saves state less often, faster execution - Best for fast pipelines where resume after restart is not critical 

Maximal durability - Saves state frequently, can resume from almost any point - Safter, but slower 

Survivable non-blocking steps - Middle ground; durable for critical points, non-blocking steps are skipped after restart - Balanced performance and durability 

What's Actually Affected:

- Checkpoint Frequency: More durability = more disk I/O and slower build 
- Resumability: More durability = better ability to recover from Jenkins restarts or crashes.
- Step Caching: Determines how much of your pipeline progress in cached or lost if Jenkins is reatarted. 

Real-World Use Cases:

Scenerio - Recommended Setting 
Fast pipelines with few risks (e.g., unit tests, static analysis) - Performance-Optimized 
Long-running jobs with approvals or user input (e.g., deployement) - Maximum durability 
Jobs where downtime is rare and you want balance - Survivable non-blocking steps 

Important Notes:

- Performance-optimized builds may not resume correctly after a jenkins restart.
- Maximum durability uses more disk and CPU but is more fault-tolerant.
- You can also set global defaults in Manage Jenkins -> Configure System -> Pipeline Speed/Durability Settings.

Preserve stashes from completed builds :

- In Jenkins Pipeline builds, you can use the stash and unstash steps to temporarily store and retrieve files between stages or even across builds. 
- By default, stash data is discarded when a build completes.
- When this checkbox is enabled, Jenkins retains the stashes even afer the build is finished, so future builds (or stages in parallel jobs) can unstash from older builds.

Use Case Example:

// Build1 
pipeline {
    agent any 
    stages {
        stage('Build'){
           steps {
		      sh 'make build'
			  stash name: 'my-artifacts', include: 'build/**'
		   }
		}		
	}
}	

// Build 2 (later or separate job)
pipeline {
    agent any 
	stages {
	   stage('Reuse Artifacts') {
	       steps {
		      unstash 'my-artifacts'
			  sh 'deploy build/'
		   }
	   }
	}
}

- Without Preserve stashes from completed builds, the unstash in Build 2 will fail.

Real-World Scenarios:

Scenario - why Preserve Stash?
Deploy pipeline needs artifacts from a prior build - To avoid re-building the same code
Split build & deploy into different jobs - Share build output between pipelines 
Run tests on the same artifacts after build finishes - Test in another agent or delayed job 
Manual rollback or debugging - Reuse previous build artifacts without re-run 

Considerations:

Risk - Description 
Disk space usage - Stashed files are retained longer, increasing storage 
Manual cleanup may be required - Consider using stash includes wisely or archiving artifacts instead. 

Best Practices: 

- Use stash + unstash for short-lived sharing (within or between builds).
- Use "Preserve Stashes" only if:
   - you need to access the same stash across builds or jobs.
   - you don't want to archive files permanently as artifacts. 
- For long-term storage, prefer archiveArtifacts.

  Schedule:
      - This file follows the syntax of cron (with minor differences).
	  - Specifically, each line consists of fields separated by TAB or whitespace:
	    MINUTE(0-59) HOUR(0-23) DOM(1-31) MONTH(1-12) DOW(0-7) where 0 and 7 are sunday.
      To specify multiple values for one field, the following operators are available. In the order of precedence. 
	  -  * specifies all valid values.
	  -  * M-N specifies a range of values.
	  -  * M-N/X or */X steps by intervals of X trhough the specified range or whole valid range 
	  -  * A,B,...,Z enumerates multiple values. 
	  
	  -To allow periodically scheduled task to produce even load on the system, the symbol H (for "hash") should be used whenever possible.
	  -For example, using 0 0 * * * for a dozen daily jobs will cause a large spike at midnight.
	  -In contrast, using H H * * * would still execute each job once a day, but not all at the same time, better using limited resources.
	  
	  - The H symbol can be used with a range, For example, H H(0-7) * * * means some time between 12:00 AM (midnight) to 7:59 AM.
	  - You can also use step intervals with H with or without ranges.
	  
	  - The H symbol can be though of as a random value over a range., but it acutally is a hash of the job name, not a random function,
	    so that the value remains stable for any given project. 
		
	  - Beware that for the day of month field, short cycles such as */3 or H/3 will not work consistently near the end of the most months, due to variable month lengths.
	  - For example */3 will run to the 1st,4th,..31th days of a long month, then again the next day of the next month.
	  - Hashes are always chosen in the 1-28 days range, so H/3 will produce a gap between runs of between 3 and 6 days at the end of a month. 
	    (Longer cycles will also have inconsistent lengths but the effect may be relatively less noticeable.)
		
		Empty lines and lines that start with # will be ignored as comments.
		
		In addtion, @yearly, @annually,@monthly,@weekly,@daily,@midnight,and @hourly are supported as convenient aliases.
		These use the hash system for automatic balancing. 
		For example, @hourly is the same as H * * * * * and could mean at any time the hour. 
		             @midnight actually means some time between 12:00 AM and 2:59 AM.
					 
		Examples:
		# Every fifteen minutes (perhaps at :07, :22, :37, :52):
		H/15 * * * * 
		# Every ten minutes in the first half of every hours (three times, perhaps at :04, :14, :24):
		H(0-29)/10 * * * *
		# Once every two hours at 45 minutes past the hour starting at 09:45 AM and finishing at 3:45 PM every weekday.
		45 9-16/2 * * 1-5 
		# Once in every two hours slot between 8 AM and 4 PM every weekday (perhaps at 9:38 AM, 11:38 AN, 1:39=8 PM, 3:38 PM):
		H H(8-15)/2 * * 1-5
		# Once a day on the 1st and 15th of every month except december:
		H H 1,15 1-11 *

3, Explain Jenkins Pipeline?
A,
- A Jenkins Pipeline is a way to define your build, test and deployment process as code.
- Pipelines can be written using Declarative or Scripted.

Example:
pipeline {
-> It is the starting point of jenkins declartive pipeline.
-> Without it - Jenkins won't recognise the file as a pipeline. 
    agent any 
	-> Says: "Run this pipeline on any available Jenkins node/agent"
	-> you can also specify: 
	   - agent none -> no default agent.
	   - agent { docker { image 'maven:3.8.1' } } -> run inside a Docker container. 
	stages {
	-> Collection of steps grouped by phases.
	-> Each stage represents one logical step (Build, Test, Deploy. etc). 
	   stage('Build') {
	   -> Defines one stage.
       -> The name is what you see in Jenkins.	   
	     steps {
         -> The actual commands to run.
         -> Example: sh 'make build', echo "Hello", mvn test, docker build.		 
			echo 'Building...' 
			-> Just prints a message in Jenkins logs.
		}		 
	   }
	   stage('Test') {
	     steps {
		    echo 'Testing...' 
		 }
	   }
	   stage('Deploy') {
         steps {
           echo 'Deploying...'
		 }		 
	   }
	}
}

2, How do you handle parallel builds in Jenkins pipelines?
A,
Jenkins supports parallel stages in Declarative Pipeline.

pipeline{
   agent any
   stages {
      stage('Test') {
	      parallel {
		     stage('Unit Tests') { steps { sh 'run_unit_tests.sh' } }
			 stage('Integration Tests') { steps { sh 'run_integration_tests.sh' } }
		  }
	  }
   }
}

- Use Case : Speed up CI by running multiple test suites or deployments simultaneously.
- Caustion: Ensure enough executor resources to avoid contention.

What's an executor in Jenkins?
- Jenkins has nodes (the master and agents)
- Each node has a number of executors.
- An executor = a "worker slot" that can run one job or one stage at a time.
- If a node has 2 exeecutors -> it can run 2 things in parallel.
- if executors are all busy -> new ork has to wait in queue.

- Parallel in Declartive Pipeline 
  Example:
  pipeline {
     agent any 
	 stages {
	     stage('Parallel Work') {
             parallel {
                 stage('Job A') {
				     steps {
					 echo "Running A"
					 sleep 10
					 }
				  }
				 stage('Job B') {
				   steps {
				      echo "Running 8"
					  sleep 8
				   }
				 }
				 
             }			 
		 }
	 }
  }  
- Here, Job A and Job B try to run at the same time.

- The problem: Contention 
  - If jenkins only has 1 executor free, then both jobs cannot acutally run in parallel.
  - One will start, the other will wait in queue.
  - This is called executor contention (multiple jobs fighting for too few slots.

- The warning Means 
  - Ensure enough executor resources to avoid contention =
    "Before you use parallel() , make sure your jenkins nodes (agents) have enough executors so that each branch of your parallel block can relly run at the same time.

- How to Ensure This:
1, Check executors on Jenkins:
   - Go to Manage Jenkins -> Nodes -> Configure 
   - Set # of executors high enough for your needs.
2, Match executors to parallel branches:
   - if you run 4 parallel branches -> your node(s) mut have at least 4 executors available. 
3, or Use multiple agents. 
   stage('Parallel') {
      parallel {
	     stage('A') {
		    agent { label 'linux' }
			steps { sh 'build-a.sh' }
		 }
		 stage('B') {
		    agent { label 'windows' }
			steps { sh 'build-b.bat' }
		 }
	  }
   }
- Each branch can use a different node.

There are only 3 possible ways a Jenkins build starts in a perforce-based pipeline:
1, Perforce triggers Jenkins (via webhook/Perforce Trigger Script)
2, Jenkins triggers itself (via Polling SCM)
4, A developer triggers manually ("Build Now")

  Option B: "Perforce: Perchange Trigger" or "P4 Trigger" enabled.

What 'Poll SCM" Means (Spoon-fed explanation)

Jenkins checks perforce periodically.
For example every: 1 minute, 2 minutes, 10 minutes 
The schedule looks like: H/5 * * * * 
That means: Every 5 minutes Jenkins asks perforce: Any new changelist? Any new check-in?

If Jenkins detects a new perforce changelist -> It triggers a build automatically.
Perforce is not sending any event to Jenkins:
No Webhook, No triggers, No direct integration, Just Jenkins checking constanlty.

Open any recent build -> Console output.
The top will say:  STarted by an SCM change. 
That mesns: Jenkins detected a change while polling perforce.

**********************************************************************************************************************

Explain Poll SCM Schedule:

When you see this in Jenkins: Poll SCM: H/5 * * * *
This is a Jenkins cron schedule.
It tells Jenkins: Check perforce every 5 minutes for changes.
Let's break the meaning column by column: 
H/5 Minutes (every 5 minutes) * Hour (every hour) * Day of Month (every day) * Month (every month) * Day of week (every day)

So H/5 means: H = hash value(spread out load), /5 = every 5 mintues.

Examples you might see: H H * * *  - Once every day.

When Jenkins see this:
1, It sleeps 
2, Every X minutes, it wakesup and checks SCM (perforce)
3, if it finds new changelists -> it starts a build.

*******************************************************************************************************************

How Jenkins Detects Perforce Changes During Polling 
- this is the part most developers NEVER understand - but you will now. 
- when your Jenkins job does Poll SCM, Jenkins performs these steps:

Step1 - Jenkins remembers last build changelist 
Last build used changelist: 89231
Jenkins stores this number internally. 

Step 2 - Polling time arrives 
Example:
- Poll every 5 minutes.
- Next polling at 12:05, 12:10, 12:15...
At the polling moment, Jenkins asks perforce 
Do you have any changelists newer than 89221?

Step 3: Jenkins run a Perforce Query (internally)
- It uses the P4 plugin and internally executes a command like:
  p4 changes //your/stream/path/... @lastBuiltChangelist,now 
  This means: List all changes between the last build and now.
  Example result:
  change 89232 by dev1 on 2025/11/23
  change 89233 by dev2 on 2025/11/23 
  
Step 4: If new changelists exist -> build triggers
if results is NOT empty:
- New changelist detected.
- Jenkins says:
  Started by an SCM change.
- Jenkins syncs new files.
- Jenkins runs pipeline (Jenkinsfile)

Step 5: If no changelists -> No build 
if Perforce returns nothing:
No changes since last build 
Then Jenkins sleeps again until next polling interval.

Developer Checklist: How to know who triggered the build.

Started by an SCM change - Jenkins polling 
Started by timer - jenkins polling 
Started by p4 trigger - Perforce trigger 
Started by user - Manual build 
Started by upstream project - Pipeline chaining
