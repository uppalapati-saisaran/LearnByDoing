11, Difference between shallow copy and deep copy?
A, Shallow copy : 
    - Copies only references of nested objects.
	- makes a shallow copy - only top-level is copied.

   Deep copy : 
    - Copies actual nested objects too. 
	- copies everything recursively. 
   
import copy
original1 = [1,2,3]
original2 = [4,5,6]
shallow = copy.copy(original1)
print("Shallow Copy :",shallow)
original1.append(4);
print("Changed Original :",original1)
print("Shallow Copy Changed original :",shallow)
deep = copy.deepcopy(original2)
print("Deep Copy :",deep)
original2.append(7);
print("Changed Original :",original2)
print("Deep Copy Changed original :",deep)

Shallow Copy : [1, 2, 3]
Changed Original : [1, 2, 3, 4]
Shallow Copy Changed original : [1, 2, 3]

Deep Copy : [4, 5, 6]
Changed Original : [4, 5, 6, 7]
Deep Copy Changed original : [4, 5, 6]

12, Explain Python's garbage collection.
A, Python uses reference counting and a cyclic garbage collector to free up memory of unused objects.
-> Python uses reference counting as its primary garbage collection mechanism, where each object keeps track of how many references point to it.
   When the count goes to zero, the object is automatically deleted.
# Example: Reference Couting in Python  
import sys
#create an object(a simple list)
my_list = [1,2,3]
#check the reference count using sys.getrefcount()
print("Initial reference count:",sys.getrefcount(my_list))
#create another reference to the same list.
another_ref = my_list 
print("Reference count after new list reference:",sys.getrefcount(my_list))
#Remove one reference 
del another_ref 
print("Reference count after deleting one reference:", sys.getrefcount(my_list))
#Remove the last reference 
del my_list  # Now the reference becomes 0, and the object is garbage collected.

-> A Circular reference occurs when two or more objects reference each other, preventing Python's reference counter from detecting that they are no longer in use.
-> Python's garbage collector(GC) can detect and clean up these cycles.
#Example:Cyclic References in Python 
import gc 
class Node:
    def __init__(self,name):
        self.name = name
        self.other = None
        
    def __del__(self):
        print(f"{self.name} destoryed")
#create two objects that reference each other.
a = Node("A")
b = Node("B")
a.other = b 
b.other = a 
#Remove references from the main scope 
del a 
del b 
#At this point, the objects are still in memory due to circular reference 
print("Collecting garbage...")
#Manually trigger garbage collection 
gc.collect()

14, What is the Global Interpreter Lock(GIL)?
A, GIL is a mutex in CPython that allows only one thread to execute Python bytecode at a time, limiting true parallelism.
-> how it affects multithreading when working with CPU-bound tasks.

# GIL Example: Multithreading vs Multiprocessing 
# CPU-Bound Task (like calculating factorial of large numbers)

import threading 
import multiprocessing 
import time 

def cpu_bound_work():
    # A CPU-intenstive task (factorial calculation)
    x = 1 
    for i in range(1,50000):
        x *= i 
        
def run_threads():
    threads = [] 
    for _ in range(4):
        t = threading.Thread(target=cpu_bound_work)
        threads.append(t)
        t.start() 
    for t in threads:
        t.join() 
        
def run_processes():
    processes = []
    for _ in range(4):
        p = multiprocessing.Process(target=cpu_bound_work)
        processes.append(p)
        p.start()
    for p in processes:
        p.join() 
        
if __name__ == "__main__":
    start = time.time()
    run_threads()
    print(f"Threading took {time.time() - start:.2f} seconds")
    
    start = time.time()
    run_processes() 
    print(f"Multiprocessing took {time.time() - start:.2f} seconds")
	
output:

Threading took 3.54 seconds
Process took 3.10 seconds

38, Dict vs defaultdict 
- defaultdict is a subclass of the built-in dict class, provided by the collections module.
- It overrides one method and provides a default value for the key that does not exist.

Why use defaultdict?
- Normally, accessing a non-existent key in a regular dicitionary throws a KeyError.
- defaultdict solves this by providing a default value automatically when a key is not found.

Syntax:
from collections import defaultdict 
d = defaultdict(default_factory)

- default_factory is a function that provides the default value(like int, list, set. etc.)

Example1: Counting Elements with int (returns 0 by default)
from collections import defaultdict
word_count = defaultdict(int)
sentence = "hello world hello python"
for word in sentence.split():
    word_count[word] += 1 
print(word_count)

defaultdict(<class 'int'>, {'hello':2, 'world':1, 'python':1})

    seen = {}
    for i,n in enumerate(nums):
        if target - n in seen:
            return [seen[target - n], i]
        seen[n] = i

48, Algorithm

1, Reverse a linked list:

class Node:
    def __init__(self,data):
        self.data = data;
        self.next = None 

class linklist:
    def __init__(self):
        self.head = None
    #Insert at end 
    def append(self,data):
        new_node = Node(data)
        if not self.head:
            self.head = new_node 
            return 
        
        current = self.head 
        while current.next:
            current = current.next 
        current.next = new_node 
    
    def print(self):
        if not self.head:
            print("No nodes in the linklist")
            return 
        current = self.head
        while(current != None):
            print(f" -> {current.data}",end = " ")

def binary_search(arr,target):
    left = 0
    right = len(arr)-1 
    
    while left <= right:
        mid = (left + right) // 2
        if arr[mid] == target:
            return mid # Target found at index mid 
        elif arr[mid] < target:
            left = mid + 1 
        else:
            right = mid - 1
            
    return -1

Software entities (Classes, modules, functions) should be open for extension, but closed for modification.

What does it mean?
- Open for extension: you should be able to add new features easily.

 - Makes code easier to maintain and scale.

How does Python's Global interpreter lock (GIL) affect multi-thread programs?
A,
- The GIL allows only one thread to execute Python bytecode at a time-- even on multi-core processors.
- This means CPU-bound programs (like heavy computations) don't benefit much from threads.
- I/O - bound programs (e.g., file or network operations) still benefit from threading.

Use multiprocessing for parallel CPU-bound tasks.

What is concurrency?

- Concurrency means: running multiple tasks at the same time(or almost at the same time), so your program is faster and more responsive.
- Think of it like a kichen where:
   - The chef is boiling rice,
   - At the same time frying vegetables,
   - And making tea 
- All tasks are happening side-by-side using threads or processes. 

Python concurrency Modules 

There are 3 main ways to achieve concurrenty in Python:
threading - Best for I/O-bound tasks( like reading files,networks calls)
multiprocessing - Best for CPU-bound tasks ( heavy calculation )
asyncio - Best for async I/O ( web APIs,DB calls, etc.) 

Let's start with the easiest one:

Example: Concurrency using threading 
We'll create two tasks:
- One function prints "Boiling noodles"
- Another prints "Frying egg"
They'll run at the same time using thread.

code with spoon-fed explanation:

import threading # This module helps us create threads 
import time  # To simulate time delays 

# Taks1 : Boil noodles 
def boil_noodles():
    for i in range(3):
	    print("Boiling noodles...");
		time.sleep(1) # Simulate 1-second delay 
		
# Task2 : Fry egg 
def fry_egg():
    for i in range(3):
	    print("Frying egg...")
		time.sleep(1) # Simulate 1-second delay 

# Create a thread for each task 
thread1 = threading.Thread(target=boil_noodles)
thread2 = threading.Thread(target=fry_egg) 

#Start both threads (runs in parallel) 
thread1.start();
thread2.start() 

#Wait for both tasks to complete
thread1.join()
thread2.join() 

print("Breakfast ready!") 

What Happnes Here?

threading.Thread(...) - Create a thread to run the function 
start() - Begin running that thread 
sleep(1) - Simulates the task taking 1 second 
join() - Wait until the thread finishes before moving on 
Result - Both taks run together instead of one after on other

What is concurrencty with Threads?
- Concurrency using threads is a way to run multiple tasks at (almost) the same time- within the same program, using shared memory. 
- It's iike:
  * One brain (Python program)
  * Doing many things at once (using threads like boiling, frying) 
  
Why Use Threads?
- improves performance when tasks involve waiting (like file I/O, web calls).
- Threads are lightweight (shared memory, no need to copy data).
- Used in real-time systems, games, servers, GUIs 

Python Limitation: GIL ( Global Interpreter Lock )
- Python has a lock that allows only one thread to execute Python bytecode at a time. 

Important:
- Threads work well for I/O-bound tasks (waiting for files, network, etc.) 
- Not good for CPU-bound tasks(heavy calculations) -> Use multiprocessing instead 

Thread - A small task insidea program that can run indpendently.
Main Thread - The default thread that starts first 
start() - Begins the thread execution 
join() - Waits for the thread to finish 
daemon - Runs in background, killed when the main program ends 
Shared memory - Threads cna access same variables

- Both threads read/write the same shared_list.

Race Conditions and Synchorization:

Problem: Race condition
- When two threads access the same variable at the same time,it can cause weird, buggy behaviour 
Example:
- Thread 1 writes to a file 
- Thread 2 reads from the same file 
*** Conflicit! ***

Solution: Use Locks to synchronize 
lock = threading.Lock() #  Create lock 

def safe_add():
    for i in range(5):
	    with lock: # Only one thread can enter here at a time 
		   shared_list.append(i)

import threading
import requests
from tqdm import tqdm

#List of image URLs
image_urls = [
  "http://picsum.photos/500/300",
  "http://picsum.photos/600/400",
  "http://picsum.photos/700/500" 
]

# Thread worker function with progress bar 
def download_image_with_progress(url, filename):
    print(f"[START] Downloading {filename}")
	
	response = requests.get(url,stream=True) #stream=True 
	total_size = int(response.headers.get('content-length',0)) 
	chunk_size = 1024 #1KB 
	
	with open(filename, "wb") as f, tqdm(
	     desc=filename,
		 total=total_size,
		 unit="8",
		 unit_scale=True,
		 unit_divisor=1024,
		 leave=True
	) as bar: 
	   for chunk in response.iter_content(chunk_size=chunk_size):
	       if chunk:
		      f.write(chunk)
			  bar.update(len(chunk)) 
	
	print(f"[DONE] {filename} downloaded.")
	
# Create and start threads 
threads = []

for i,url in enumerate(image_urls):
    filename = f"image_{i}.jpg"
    t = threading.Thread(target=download_image_with_progress, args=(url, filename))
    threads.append(t)
    t.start() 

# Wait for all threads to finish 
for t in threads:
    t.join() 

print("All images download with progress.")

Line - Explanation

tqdm(...) - Creates a progress bar 
response.iter_content(...) - Reads file in chunks of 1KB 
bar.update(len(chunk)) - Move the progress bar forward as each chunk is written.
threading.Thread(...) - Runs each download in its own thread

Why Use Multiprocessing?

- Python's GIL blocks true multi-core execution for CPU-bound code.
- Multiprocesssing bypasses the GIL by creating separate processes, each with its own Python Interpreter and memory space.
- Great for tasks like data crunching, image processing, or scientific computing. 

Thread vs PRocesses 

Feature-Threads-Processes  
1, Memory-Shared-Separate 
2, GIL Impact- Yes (no real parallel CPU use)- No (paralled across cores)
3, Best for - I/O-bound (network,disk) - CPU-bound(heavy computation) 
4, Overhead - Low (cheap context switches) - Higher (process creation & IPC costs)

Concept 10: Context Manager (with keyword) 

What is a Context Manager?
A,
A context manager is used to manage resources(like files, DB connections) safetly and automatically -
without forgetting to close or clean up.

Basic Syntax:

with open("file.txt","r") as f:
    data = f.read() 

As soon as the block ends, the file is automatically closed - even if there's an error. 

Without with (not safe):
f = open("file.txt","r")
data=f.read()
f.close() # You must remember to close 

If you program crashes before .close() the file stays open!

Safe way with with:
with open("file.txt","r") as f:
   print(f.read()) 
Even if an error occurs inside the block, Python closes the file. 

Used in Read Life For:
Resource Type  - Example 
File handling - with open(...)
DB connection - with db.connect() as conn:
Lock(thread) - with lock 
Temporary files - with tempfile.TemporaryFile() 

How it Works internally:
When you use with, Python looks for two special methods:
. __enter__  - What to do when block starts
. __exit__ - What to do when block ends 

Example with your own class:

class MyManager:
  def __enter__(self):
     print("Start")
     return self 
 
  def __exit__(self,exc_type,exc_val,exc_tb):
     print("End") 
	 
with MyManager():
    print("Doing work")
	
with MyManager():
   print("Doing work")

What is __eq__ in Python?

__eq__ is a special method that tells Python how to compare two objects using the == operator.

Think of it like this:
__eq__ answers the question: Are these two objects equal? 

Default behaviour without __eq__
class Dog:
    def __init__(self,name):
	    self.name = name 
		
dog1 = Dog("Bruno")
dog2 = Dog("Bruno")

print(dog1 == dog2)

Output:
False 

Why?
Because by default, Python checks if they are the same object in memory, not if their values are equal.

Let's fix that with __eq__

class Dog:
    def __init__(self,name):
	    self.name = name 
		
	def __eq__(self,other):
	    return self.name == other.name 
		
dog1 = Dog("Bruno")
dog2 = Dog("Bruno")

print(dog1 == dog2)

Output:
True 
Now Python knows: If two dogs have the same name, they are equal 

A Better Example with Multiple Attributes 

class Book:
    def __init__(self,title,author):
	    self.title = title 
		self.author = author 
		
	def __eq__(self,other):
	    return self.title == other.title 
		
book1 = Book("Harry Potter", "J.K. Rowling")
book2 = Book("Harry Potter", "J.K. Rowling") 
book3 = Book("Percy Jackson", "Rick Riordan") 

print(book1 == book2) # True 
print(book1 == book3) # False 

Bonus: Add __repr__ for Better Display 

class Book:

The @property decorator in Python is used to define a method that behaves like an attribute.
It allows you to define getter.setter and deleter functions for a class attribute in an elegant and Pythonic way. 

Use case: Why Use @property?
When you want:
1, Attribute-like access (e.g,. obj.attr) with additional logic.
2, To hide internal data (encapsulation).
3, To control access  to class attributes(validation, computation).

Basic Example with Line-By-Line Explanation:
Let's look at a complete example of a class using @property, @<property>.setter, and @<property>.deleter.

Example: Temperature Converter (Celsius <-> Fahrenheit) 

class Temperature:
// Defines a class named Temperature.
    def __init__(self, celsisus):
	// The __init__method initialze the class with a temperature in Celslus.
	    self._celsisus = celsisus 
		// _celsius is a private-like variable (conventionally prefixed with _ to include internal use). 
	  
	@property
	def celsisus(self):
	    """Getter with validation"""
		return self._celsisus 
	// @property turns the method celsius() into a getter
	// Now you can do: temp.celsius instead of temp.celsius().
	// This allows attribute style access while still using a method internally. 
		
	@celsius.setter 
    def celsisu(self, value):
	    """Setter with validation"""
		if value < -273.15:
		   raise ValueError("Temperature below -273.15 C is not possible.")
        self._celsisus = value 		
	// The @celsisus.setter defines a setter method for celsius.
	// You can now do temp.celsisus = 25, and it will run the logic.
	// It validate the input and only then updates _celisus 
	
    @property
    def fahrenheit(self):
        """Computed property, no setter defined"""
        return (self._celsius * 9/5) + 32 
    // This is another computed property.
    // It does not have a setter, so temp.fahrenheit = 90 will raise an error.
    // Every time you access temp.fahrenheit, it computes it from _celsius.
	
	Usage:
	temp = Temperature(25)  # Set initial temperature  
	print(temp.celsius)     # Accesses the @poperty getter 
	temp.celsisus = 30      # Calls the @property setter 
	print(temp.fahrenheit)  # Calls the @property method -> 86.0 
	temp.celsius = -300     # Raises ValueError (because of validation) 
	
Benefits of Using @property 
Feature - with @property 
Clean attribute syntax - obj.attr 
Built-in validation - Yes 
Computed values - Yes(@property) 
Encapsulation Easy via _attr

Summary
- Use @property when you want to add logic to attribute access without changing the syntax. 
- Helps enforce encapsulation and validation while keeping your API user-friendly.
- You can define 
   - @property -> getter 
   - @<property>.setter 
   - @<property>.deleter -> deleter

What is @classmethod?

- @classmethod is a decorator used to define a class-level method.
- Unlike a regular method (which takes self), a class method takes cls as the first parameter.
- It can access or modify class state(i.e., class variables) but not instance state directly.
- It is commonly used for:
  - Alternative constructors 
  - Factory methods 
  - Modifying class variables.
  
Example: Alternate Constructor Using @classmethod

     raise_percentage = 1.05

	     self.name = name 
		 self.salary = salary

	     self.salary *= self.raise_percentage

	 @classmethod 
	 // This tells Python that the method that follows is a class method, not an instance method 
	 def from_string(cls, emp_str):
	     ""Alternatvie constructor to create an object from a string.""" 
		 name, salary = emp_str.split("-")
		 return cls(name, float(salary)) 
	 // cls refers to the class itself,not an instance. 
	 // The method parses the input string (like "Alice-50000") and returns a new instance of the class using cls(...).
	 // This is a common alternative constructor pattern

What is a Stack?

A Stack is a data structure where:
- The last item added is the first one to come out.
- This is called LIFO: Last in, First Out. 

Think of it like: A stack of plates - you can only take the top plate first.

Operations in Stack:

- There are 2 main operations:

1, Push(Item) -> Add item to the top.
2, pop() -> Remove the top item.

Ohters(optional):
3, peek() -> Look at the top item.
4, is_empty() -> Check if the stack is empty.

Use Cases of Stack:

- Undo feature in apps(last change removed first)
- Backtracking (games, puzzles)
- Function calls (when a function calls another, and so on)
- Expression parsing (like (a + b)*c)
- Browser history (go back to the last page)

What is a Queue?

A queue is a data structure where:
- The first item added is the first one to come out.
- This is called FIFO: First In,First Out
Think of it like: People standing in a line: The person who comes first, leaves first.

Operations in Queue:
1, enqueue(item) -> Add item at the end of the queue.
2, dequeue() -> Remove item from the front.

Optional:
3, peek() -> See the item at the front.
4, is_empty() -> Check if the queue is empty.

Use Cases of Queue:
- Print Queue(printer prints first request first)
- Customer Service Queue 
- Task scheduling (like CPU task queue)
- Breadth-First Search in algorithms
- Data streaming (process oldest data first)

Here's a simple min-heap class without using heapq: 

class MinHeap:
    def __init__(self):
       self.heap = []

    def insert(self, val):
       self.heap.append(val)
	   self._heapify_up(len(self.heap)-1) 
	   
	def pop(self):
	   if len(self.heap) == 0:
	      return None 
	   self._swap(0, len(self.heap)- 1)
       min_val = self.heap.pop()
       self._heapify_down(0)
       return min_val 
 
    def _heapify_up(self, index):
        parent = (index - 1) // 2 
        if index > 0 and self.heap[index] < self.heap[parent]:
           self._swap(index,parent)
           self._heapify_up(parent) 

    def __headify_down(self,index):
        left = 2 * index + 1 
       right = 2 * index + 2 
       smallest = index 
        
       if left < len(self.heap) and self.heap[left] < self.heap[smallest]:
	       smallest = left 
		   
	   if right < len(self.heap) and self.heap[right] < self.heap[smallest]:
	       smallest = right 
		   
	   if smallest != index:
	       self._swap(index, smallest)
		   self._heapify_down(smallest)
		   
	def _swap(self, i, j):
	    self.heap[i],self.heap[j] = self.heap[j], self.heap[i]

def interpolation_search(arr, target):
    low, high = 0, len(arr) - 1 
	
	while low <= high and arr[low] <= target <= arr[high]:
	    pos = low + ((high -low) * (target - arr[low]) // (arr[high] - arr[low]))

		   return pos

def merge(left, right):
    result = []
    i = j = 0 
    while i < len(left) and j < len(right):
        if left[i] <= right[i]:
            result.append(left[i])
            i += 1  
        else:
            result.append(right[j])
            j += 1 
    result.extend(left[i:])
    result.extend(right[j:])

The SOLID principles are five foudational design principles that help developers write cleaner, more maintainable, 
and scalable software - regardless of the language.

1, S - Single Responsibility Principle (SRP) 
- A class should have only one reason to change. 

Python Example:

   def __init__(self,content):
       self.content = content 
	   
   def generate(self):
      return f"Report: {self.content}"

	    print(report.generate()) 
		
USe Case: Separating report generation from report presentation. 

Real-World Scenario: In a billing system, the logic tha calculates an invoice shouldn't also be responsible for sending it via email. 

2. O - Open/Closed Principle (OCP) 
- Software entities should be open for extension but closed for modification. 

Python Example:
from abc import ABC, abstractmethod 

class PaymentProcessor(ABC):
   @abstractmethod 
   def pay(self, amount): pass

   def pay(self, amount):
       print(f"Paid {amount} using PayPal.")

   def pay(self,amount):
       print(f"Paid {amount} using Stripe.")

def process_payment(processor: PaymentProcessor, amount):
   processor.pay(amount) 

USe Case: Easily add new payment methods without touching existing logic. 

Real-World Scenario: Adding a new crypto payment option to an e-commerence platform without breaking current code.

3. L - Liskov Substitution Principle (LSP)
- Derived classses must be substitutable for their base classes. 

Python Example:
class Bird:
   def fly(self):
       pass 
	   
class Sparrow(Bird):
   def fly(self):
       print("Sparrow flying")

#Wrong

   def fly(self):
      raise NotImplmentedError("Ostrich can't fly") 
	  
Use Case: Avoid designing hierarchies where child classes break parent expectations. 
Real-World Scenario: Avoid creating APIs that allow invalid subsitutions (e.g., a mute speaker in a sound system hierarchy).

4. I - Interface Segregation Principle (ISP)
- Clients should not be forced to depend on interfaces they do not use. 
- Python Example using Abstract Base Classes:

DRY in Software: DRY = Don't Repeat Yourself 

Definition: DRY is a software developement principle aimed at reducing duplication of code, logic, or data. 

"Every piece of knowledge must have a single, unambiguous, authoritative representation within a system". 

Goal:
Avoid repetition to:

- Improve maintainability 
- Reduce bugs 
- Make code cleaner and more modular.
- Enable reuse 

Why is repetition bad?
- Changes must be made in multiple places, increasing chances of mistakes.
- Duplicated logic leads to inconsistent behaviour. 
- More code means more testing and debugging. 

Example in Python:

Without DRY:

    #Connect to database 
	conn = connect_to_db()
	cursor = conn.cursor()
	#Fetch user 
	cursor.execute("SELECT * FROM users")
	return cursor.fetchall()

    #Connect to database 
    conn = connect_to_db() 
    cursor = conn.cursor() 
    # Fetch orders 
    cursor.execute("SELECT * FROM orders")
    return cursor.fetchall() 

With DRY:

def fetch_data(query):
     conn = connect_to_db()
     cursor = conn.cursor()
     cursor.execute(query)
     return cursor.fetchall() 

#Reuse:
users = fetch_data("SELECT * FROM users")
orders = fetch_data("SELECT * FROM orders")

Be Careful of:
- Over-abstraction following DRY too aggressively can lead to unreadable or over engineered code.

 What is Separation of Concerns (Soc)?
Separation of concerns is a software design principle wehre a program is divided into distinct sections, each responsible 
   for one specific functionality or concern.
   - Each module/class/function does one thing and nothing else. 
   - Make code cleaner, easiter to maintain, test and extend. 
   
Think of it like a restaurant kitchen:
 - One chef handles appetizers, another desserts, another main course.
 - They don't all do everything, which avoids confusion and mistakes.
 

Example in Python (Simple)
- Suppose we have program to register a user, save to DB, and send email.

Bad Design (No Soc)

def register_user(name,email):
   #Validate input 
   if not name or not email:
      return "Invalid input"
	  
   #Save to database 
   conn = open_db_connection()
   conn.execute(f"INSERT INTO users(name,email) VALUES('{name}','{email}')")
   conn.close()
   
   #Send welcome email 
   send_email(email, "Welcome!", "Thanks for registering")
   
Problems:
- Single function does 3 different things: validation, database, email 
- Hard to test or reuse parts individually.

Good design (with SOC)

def validate_user(name,email):
    if not name or not email:
	    raise ValueError("Invalid input") 
		
def save_user_to_db(name,email):
    conn = open_db_connection()
	conn.execute(f"INSERT INTO users(name,email)) VALUES('{name}','{email}')")
	conn.close() 

def send_welcome_email(email):
   send_email(email, "Welcome!", "Thanks for registering")
   
def register_user(name,email):
    validate_user(name,email)
	save_user_to_db(name,email)
	send_welcome_email(email)
	
Advantages:
- Each function handles one concern.
- Easy to test validate_user() independently.
- Easy to replace setn_welcome_email() with another emall system
- Clear, readable, maintaintable code.

Singleton Design Pattern:

What is it?
- The singleton pattern ensures that a class has only ONE instance during the entire program.
- No matter how many times you try to clean an object, you always get the same instance. 

Think of it like:
- A company has only one CEO. Even if 100 employees say "I want a CEO", they all point to the same person.

Basic Example in Python:

class Singleton:
     _instance = None # class variable to hold the single instance. 
	 
	 def __new__(cls, *args, **kwargs):
	     if not cls._instance:  # if no instance exists 
		    cls._instance = super().__new__(cls) # create one 
	     return cls._instance  # always return the same instance  
		 
# Test 
a = Singleton() 
b = Singleton() 

print( a is b) # True -> both point to the same object

Output: True 

- With Real Data (Logger Example) 

class Logger:
    __instance = None 
	
	def __new__(cls, *args, **kwargs):
	    if not cls._instance:
		   cls._instance = super().__new__(cls)
		   cls._instance.log_file = "app.log" 
		return cls_instance
		
	def log(self,message):
	    with open(self.log_file, "a") as f:
		     f.write(message + "\n")
			 
# Test 
logger1 = Logger()
logger2 = Logger() 

logger1.log("App started")
logger2.log("User logged in")

print(logger1 is logger2) # True 

- Even though we created logger1 and logger2, both write to the same log file.
That's singleton in action. 

- Use Cases in Real-Time Projects:
1, Logging System -> Only one logger should exist to write logs.
2, Configuration Manager -> App-Wide setting should be consistent.
3, Database Connection Pool -> Only one connection manager per BD 
4, Caching -> A single cache shared across the app.
5, Thread Pool -> Single manager to handle threads. 

Real-Life Analogy:
- printer spooler -> Only one spooler manages all print jobs.
- Windows Task Manager -> Only one instance can run at a time.
- Operating System Kernel -> Only one kernel running in system memory. 

Pros & Cons 
Advantages:
- Ensures a single point of access.
- Saves memory (no duplicate objects)
- Useful for shared resources.

Disadvantages:
- Can hide bad design (global state abuse)
- Harder to test (mocking is tricky).
- In multihread environments, need extra care (thread safety).

Thread-Safe Singleton in Python 

Problem in Multi-threading 

Imagine two threads running at the same time:
  - Thread A checks _instance is None -> True 
  - Thread B checks _instance is None -> True 
    -> Both create an object -> You end up with two instances.
  That breaks the Singleton rule.
  
Solution: Use a Locks
We use Python's threading.Lock() to ensure only one thread can create the instance at a time.

Example: Thread-Safe Singleton 

import threading 

class Singleton:
    _instance = None 
	_lock = threading.Lock() # Lock object 
	
	def __new__(cls, *args, **kwargs):
	   if not cls._instance:
	      with cls._lock: #Only one thread enters here at a time.
		      if not cls._instance: # Double-check inside lock 
			      cls._instance = super().__new__(cls) 
	   return cls._instance 
	   
	#Test with threads 
	def create_singleton():
	   obj = Singleton()
       print(f"Object ID: {id(obj)}") 

    threads = [] 
  	for i in range(5):
        t = threading.Thread(target=create_singleton)
        threads.append(t)
        t. start() 

    for t in threads:
      t.join()

Output:

 	Object ID : 1400781
    Object ID : 1400781
	Object ID : 1400781
	Object ID : 1400781
	
- No matter how many threads try, only one object is created. 

Real-World Scenarios for Thread Safe Singleton:
1, Database Connection Pool 
   - If multiple threads try to connect, you want one connection manager.
2, Logger 
   - Logs from different threads should go to the same log.
3, Configuration Loader 
   - All threads must use the same config object. 
   
Alternative: Singleton with @decorator 
Python's flexibility lets us simplify Singleton using a decorator:

Factory Method Pattern

What is it?
- Factory method is a creational design pattern.
- Instead of creating objects directly using ClassName(), you can a factory method that decides which object to create.

It's like a Pizza Shop - you don't directly make pizza yourself. You ask the factory (pizza shop), and it gives your the right type of pizza. 

Without Factory (Naive Way)

class Dog:
    def speak(self):
	    return "Woof!" 
		
class Cat:
    def speak(self):
	    return "Meow!" 
		
#Client code 
pet_type = "Dog"

if pet_type == "dog":
   pet = Dog() 
elif pet_type == "cat":
   pet = Cat() 
else:
   raise ValueError("Unknown pet type") 
 
 print(pet.speak()) 
 
 Problem: The client code (if/else) knows all the details 
 if we add a new animal (e.g., Bird), we must change this code.
 That violates Separation of Concerns & Open/Closed Principles.
 
#Factory 
With Factory Method 
We move object creation into a factory class/function 

class Dog:
   def speak(self):
       return "Woof!"

class Cat:
   def speak(self):
       return "Meow!"
	   
#Factory 
class PetFactory:
   @staticmethod 
   def get_pet(pet_type):
       if pet_type == "dog":
	      return Dog()
	   elif pet_type == "cat":
	      return Cat() 
	   else:
	      raise ValueError("Unknown pet type") 

#Clien type 
pet = PetFactory.get_pet("dog")
print(pet.speak()) 

Now if we add Bird, we only update the factoyr, not the client code.

Real-World Example: Database Connector 

- Image a project that can use MySQL or PostgreSQL
- Instead of hardcoding connecion logic everywhere , we use a factory.

class MySQLDatabase:
   def connect(self):
      return "Connect to MySQL" 
	 
class PostgresDatabase:
   def connect(self):
      return "Connected to PostgreSQL" 
	  
class DatabaseFactory:
   @staticmethod 
   def get_database(db_type):
       if db_type == "mysql":
          return MySQLDatabase() 
       elif db_type == "postgres":
          return PostgreDatabase() 
       else:
          raise ValueError("Unknown database type")

#client code 
db = DatabaseFactory.get_database("postgre")
print(db.connect()) # Connected to PostgreSQL
- The client code doesn't care hwo the object is created. 

Use Cases in Real-Time Projects:
1, Database connections -> Choose DB at runtime.
2, UI Widgets - A factory gives buttons/sliders for different OS (Windows, Mac, Linux)
3, Payment Gateway - Factory decides whether to return PayPal, Stripe, or CreditCard processor. 
4, Message Queue Client - Factory provides kafka, RabbitMQ, or SQS client 
5, File Parser - Factory returns JSONParser, XML Parser, or CVS Parser 

Pros &  Cros:
Advantages: 
1, Removes  if/else clutter from client code.
2, Makes code extensible (easier to add new types)
3, Follows Open/Closed Principle (open for extension, closed for modification).
Disadvantages:
1, More classes -> Slightly more complexity
2, For every small projects, it may be overkill.

Quick Anaology:
- Without factory - You cook pizza yourself, handling dough, sauce, toppings.
- With factory - You just say "Give me a Pepperoni pizza" and the shop handles the rest.

Observer Pattern:

What is it?
- Observer is a behavioural design pattern.
- It defines a one-to-many relationship between objects.
- When one object (Subject) changes state, all its dependents (Observers) are notified automatically.

Think of it like YouTube Subscribers:
- You (The subject) upload a new video.
- All subscribers (Observers) get nodifired immediately.

With out Observer (Naive way):

class NewsAgency:
    def __init__(self):
        self.news = None 

    def set_news(self, news):
        self.news = news 
        print(f"News Agency: {news}") 

        #Directly notify channels (bad!)
        tv = TVChannel() 
        tv.update(news)
        paper = Newspaper()
        paper.update(news) 

class TVChannel:
     def update(self,news): 
         print(f"TV Channel shows: {news}") 

class NewsPaper:
     def update(self,news):
         print(f"{Newspaper prints: {news}")

agency = NewsAgency()
agency.set_news("New policy annoucned!") 

Problem: NewsAgency is hardcoded to know about TVChannel and Newspaper.
- if we add MobileApp, we must modify NewsAgency - > Violates Open/Closed Principle. 

With Observer Pattern 
- We decouple them using Subject + Observers 

class NewAgency:
    def __init__(self):
      self.observers = [] #List of subscribers 
      self.news = None 
    
    def add_observer(self,observer): 
        self.observers.append(observer) 
  
    def remove_observer(self,observer):
        self.observers.remove(observer)
  
    def set_news(self,news):
       self.news = news
       self.notify_all() 

    def notify_all(self):
       for observer in self.observers:
           observer.update(self.news) 
   
$Observer Interface 
class Observer:
   def update(self,news):
      pass 

#Concrete Observers
class TVChannel(Observer):
   def update(self, news):
     print(f"TV Channel shows: {news}") 

class Newspaper(Observer):
   def update(self,news):
     print(f"Newspaper prints: {news}") 

#Client code 
agency = NewsAgency()
tv = TVChanngle() 
paper = Newspaper() 

agency.add_observer(tv)
agency.add_observer(paper) 

agency.set_news("New policy annoucned!") 
agency.set_news("Sports event today!") 

-> Now NewsAgency doesn't know who is lisenting.
-> Observers can join/leave dynamically. 

Real-World Use Cases:

1, Event Listeners in GUI - Button click notifies listeners.
2, Stock Market App - Stock price (Subject) notifies investors (Observers1)
3, Chat Application - When a user send a message, all participants get it. 
4, Microservices - Services subscribe to events (like Kafka, RabbitMQ).
5, Logging/Monitoring - App triggers events, multiple logger/monitors observer them.

Advantages & Disadvantages:
Pros:
1, Loose coupling between Subject and Observers.
2, Easily extensible (new observers can be added without changing Subject).
3. Implements real-time event handling.

Cons:
1, if too many observers -> Performance overhead.
2, Debugging can be tricky when many observers are chained. 

Analogy:
- Without Observer - You call each friend indiviaully to tell them news.
- With Observer - You post on WhatsAPP groupm and everyone automaticially.

What is Exception handling?

Exceptions - Errors that stop your program.
Exception handling allows your program to:
- NOT Crash
- Handle errors gracefully.
- Retry operations 
- Show meanful messages.
- Log issues

Syntax:

try:
    #risk operation
except SomeSpecificError:
    #handle that error 
except:
    #handle all other errors.
else:
    #runs if no error 
finally:
    # runs ALWAYS (cleanup) 
	
Simple Example:
try:
   x = 10/0
   except ZeroDivisionError:
      print("Cannot divide by zero!")
	  
Real-World Example:

import requests

def get_weather(city):
    try:
	    response = requests.get(f"https://api.weather.com/{city}",timeout=3)
		return response.json()
	except requests.exceptions.Timeout:
        return {"error": "API timeout, please try again"} 
    except requests.exception.ConnectionErro:
        return {"error": "No internet connection"}

Used everywhere: mobile apps, websites, internal tools.

def process_payment(card):

if you don't log exceptions -> impossible to find bugs.

Advanced Real-World Pattern - Retry mechanism 

import time 

def retry(operation, retries = 3):
    for i in range(retries):
	    try:
		    return operation() 
		except Exception:
            print(f"Retry {i+1}/{retries}"}
            time.sleep(1)
    return "Failed after retries" 

Used in: Cloud systems, Payment processing, Microservices, Message queues.
