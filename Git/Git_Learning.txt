                                           1, What is Git, and how is it different from SVN (or other VCS)?
A. 
- Git is distributed version control system. Every developer has a full copy of the repository on every developer's machine, so they can work offline and commit locally. 
- Git is distributed verions control system that tracks code changes, allows collaboration, and enables branching/merging. 
- SVN is centralized, so developers depend on a central server.
- Git is faster, works offline, and supports branching/merging more efficiently. 

* Distributed - every clone is a full repository.
* Branching - lightweight and fast. 
* Staging area - allows selective commits.
* Performance - optimized for speed and large projects.

Real world use: Multiple developes working on different features can branch off, work independendly, and merge later.This avoids overwriting each other's work.

3, Explain git clone, git pull, and git fetch.
A, 
- git clone -> Copy a repository (with full history) to your machine.
  git clone -b <branch_name> <repo_rul> -> clone a specific branch in Git. 
- git pull -> Fetches + merges changes from remote to local branch.
           -> perform git fetch + git merge (or git rebase, depending on config)  
- git fetch -> Only downloads change from remote but doesn't merge 
            -> downloads changes from the remote repository but does not merge into local branches. 
			
git fetch origin main # gets changes but doesn't merge. 
git pull origin main # gets changes and merges into your local branch. 
			
* Use fetch when you want to review changes first, and pull when you want to update your branch immediately. 

Scenerio: You're in the middle of a hotfix, but your teammate pushed changes to main. Use git fetch first to review differences(git diff origin/main) before merging.

12, How do you undo the last commit but keep change?
A,
- Keep changes, remove commit:
git reset --soft HEAD~1
- HEAD moves back but working directory keeps changes.
- This removes the last commit but keeps changes in the staging area.
* HEAD~1 -> one commit before the latest commit. 
* --soft -> removes the commit but keeps your changes staged (ready for recommit). 

-Remove commit + change 
git reset --hard HEAD~1 
- HEAD -> the commit you are currently on.
- HEAD~1 -> the commit one step before HEAD.
         -> HEAD~2 = two commits before, and so on
- git reset -> Moves your branch pointer (HEAD) to another commit.
            -> Think:"rewind the branch to this commit". 
- --hard -> Move branch pointer (like normal reset)
         -> Reset staging area (index)
         -> Reset working directory (files)
         -> In short: make everything look exactly like that commit.		 

Scenerio : You accidently commited debug logs. Use reset --soft to uncommit but keep changes so you can fix and recommit ( git commit -m "Correct message". ) .

13, What is the difference between git rebase -i and git commit --amend?
A, 
git commit --amend -> Modifies the most recent commit.
                   -> lets you edit the most recent commit instead of creating a brand new one.
				   -> you can use it to:
				   1, Change the commit changes.
				   2, Add/remove fiels in the last commit
				   How it works in practice:
				   1, Change the last commit message.
				      git commit --amend
					  - Opens your editor.
					  - your can rewrite the last commit message.
					  - saves it as if that was always the message.
				   2, Add a forgotten file to the last commit.
                      Let's say you just command.
                      git commit -m "Add feature"
                      But you forget config.yml,
                      Steps:
                        - git add config.yml # stage the missing file.
                        - git commit --amend # add it to the last commit.
                   -> Now the last commit contiain both your original changes + config.yml 
Warning:
  - Amending rewrites history.
  - if you already pushed the commit to a shared branch -> amending will cause problmes for others.
  - Safe if you haven't pushed yet.   
				
git rebase -i -> interactive rebase; lets you squash, reorder, or edit multiple commits.
              -> -i = interactive rebase
			  -> it lets you edit common history: reorder, squah, edit, or delete commits.
			  -> Think of it as: "I want to go back in time and clean up my commits before sharing them".
			  -> Typical use case 
			     You've made several small or messy commits:
				   commit 1 : Add login feature 
				   commit 2 : Fix typo 
				   commit 3 : update README 
				   commit 4 : Another bugfix.
				 But before pushing, you want a cleaner history, like:
				   commit 1 : Add login feature 
				   commit 2 : Update README 
			   -> How to do it (step by step)
			      Step 1: Run interactive rebase 
				          git rebase -i HEAD~4 
				          // Means "open a interactive rebase for the last 4 commits".
				  Step 2: You'll see something like this in your editor.
				          pick a1b2c3 Add login feature 
						  pick defad Fix typo 
						  pick dfafda Update README 
						  pick jldkad Another bugfix 
						  - Each line = one commit (newest at bottom)
						  - pick = Keep commit as is 
				  Step 3: Change the commands 
				          You can replace pick with other actions:
						  - pick -> keep command 
						  - reword -> change commit message.
						  - edit -> stop and edit the commit contents
						  - squash -> merge this commit into the previous one.
						  - drop -> delete the commit.
						  Example: To squash small fixes into the main commit.
						  pick a1b2c3 Add login feature 
						  squash defad Fix typo 
						  pick dfafda Update README 
						  squash jldkad Another bugfix 
				  Step 4: Git asks for new messages 
				          If you squash, Git will show messages and let you edit them into one.
						  #This is a combination of 2 commits.
						  Add login feature 
						  Fix typo 
						  You can rewiret into 
						  Add login feature (with typo fix) 
				  Step 5: Done 
				          After saving, Git rewrites history.
						  You branch is now clear.
						  commit 1: Add login feature (with typo fix)
						  commit 2: Update README (with bugfix)
			     -> Import Warning 
				    - Just like commit -amend, rebase rewrites history.
					- Safe for local branches.
					- Avoid rebasing commits that are already pushed/shared, unless you coordinate with our team.

15, How do you find which commit introduced a bug?
A, 
Use git bisect:

git bisect start -> git bisect start 
git bisect bad -> Tell Git a bad commit (bug exists) - Usually HEAD (latest commit)  
git bisect good <commit-hash> -> Tell Git a good commit (no bug) - Some older commit 
- Git now knows, Bug introduced somewhere between good and bad. 

- Git will binary search through commits to find the one that introduced the bug.

20, You pushed sensitive info (like a password) to GitHub. How do you remove it?
A,

- Use git filter-branch (deprecated) or git filter-repo to rewrite history and remove the secret. 
- Then force-push:
  git push origin ---force 
- Also rotate the exposed credential immediately. 
- It's an official Git tool (replacement for the older git filter-branch).
- Used to rewrite history of a repository.
- You can remove files, directories, authors, or even rewrite commit messages across the entire history.
- Think of it as: Surgery on your Git history.
- Why use it? (common cases)
  1, Remove large files accidentally committed.
  2, Remove senstive info (like password, API keys)
  3, Spiit a repo -> take one folder and make it its own repo.
  4, Change author info across commits (e.g., fix email address)
  5, Clean up history before making repo public. 
- Basic usage examples:
  1, Remove a file from entire history.
     git filter-repo --path secret.txt --invert-paths 
	 - Deletes secree.txt from all commits.
  2, Remove a directory from history 
     git filter-repo --path build/ --invert-paths 
	 - Deletes everything inside build/ from all commits.
  3, Keep only one directory (split repo)
     git filter-repo --path src/ --path-rename src/:,
	 - Creates a repo with only the src/ folders as root.
  4, Replace author info 
     git filter-repo --mailmap my-mailmap.txt 
	 where my-mailmap.txt contians:
	 Old Name <old@emmil.com> New Name <new@email.com>
  5, Change commit message
     git filter-repo --message-callback '
	    return message.replace(b"TODO",b"FIXED")
     - Rewrites all commit messages, replacing "TODO" with "FIXED"
- Important notes 
  - git filter-repo rewrites history (like git rebase -i but much bigger).
  - Old commits get new hashes -> history is changed permanently.
  - After running, you usally need to force push:
    git push origin main --force 
  - Others who cloned the repo will need to re-clone (history is incompatible)
- git filter-repo = "Tool for editing Git history (remove files, rewrite authors, change messages, split repo).
- It's the modern, fast, safe replacement for git filter-branch.

Git Architecture:

1, Local Repository (Your Laptop) 
When you clone a repo, you get your own copy of the project.
- you can commit, create branches, stash , revert -> all offline. 
- Stored inside the hidden .git folder.

Important pieces inside your local Git repo:
1, Working Directory -> Your actual files (code, docs).
2, Staging Area (Index) -> Temporary area where you prepare changes before commit.
3, Local Repository -> Where commits are stored permantely on your machine. 

Command Example:
git add file.cpp # Moves file.cpp to staging area
git commit -m "Fix bug" # move changes to local respository. 

2, Remote Repository (GitHub, GitLab, Bitbucket)
- Cenratl place where everyone shares code.
- Multiple people push and pull changes.

Example:

git push origin main  # send your commit to remote 
git pull origin main  # get other's commit from remote. 

3, Git Objects 
(Backbone of Git) 
- Git is not just saving files. It stores objects in .git/objects/:
  (01) Blob (Binary large object) -> File contents (your code).
  (02) Tree -> Directory structure (like folders + file names).
  (03) Commit -> A snapshot pointing to a tree, plus metadata (author, message, timestamp)
  (04) Tag -> A label for a specific commit (like V1.0)
  
Think of it as:
   - Blob = Book content 
   - Tree = Shelf holding books 
   - Commit = Catalog entry describing shelf + book version 
   - Tag = Sticker saying "This is the release edition"
   
4, Branches (Pointers)
- A branch is just a pointer to a commit.
- main, dev, feature-xyz are just names pointing to different commits.
- HEAD -> a special pointer showing where you currently are.

git branch feature-login
git checkout feature-login 

5, Workflow in Git (Step by Step)

1. Edit files -> In working directory 
2, Stage changes -> with git add 
3, Commit snapshot -> with git commit 
4, Push to remot -> git push 
5, Others pull your changes -> with git pull 

6, Real-World Scenario: 

Image 3 developers working on a project:
- you (Local Repo) : create a feature and commit.
- Teammate A : Also commits another feature.
- Remot Repo (Git Hub) : Acts as the source of truth.

Flow:
- you both git push to remote -> history grows.
- you git pull to get teammate's changees.
- if Conflicts -> Git tells you where to fix.

      Remote Repository (Git Hub ) 
          ^        ^
          |        | 
          Local Repo 
Workign Dir -> Staging Area -> Local Commits 

In short: 

- Git = a time machine + collaboration tool 
- Everything happens first in your local repo.
- You sync with remote to share with others.
- Under the hood -> Git stores everything as object (blob, tree, commit, tag).

When to use?

Installation -> first project -> committing -> Pushing to GitHub 

Step 1: Install Git 

On Windows:
1, Got to git-scm.com 
2, Downloader the installer 
3, Run it -> Keep defaults (just click Next until finish).
4, After install, open Git Bash (you'll use this like a terminal. 

When installing Git on Windows, you have two common options:

1, Standardalone installer (Recommanded) 
-  This is the standard Git for Window installer.
-  It installs Git system-wide ( or just for your user).
-  Adds Git to your PATH ( so you can run git from command prompt, PowerShwll, or Git Bash). 
-  Comes with Git Bash, Git GUI, and integration with Windows context menu (right clock -> "Git Bash here")
-  Easier to update later.
-  Best if you are setting up Git for development on your computer.
-  This is what most developers use. 

2, Portable Version 
- No installation required - you just unzip and run 
- Doest not add Git to PATH automatically.
- No Context menu integration 
- Good for 
     - Running Git from a USB Stick.
	 - Using a machines where you don't admin rigthts. 
	 - Keeping multiple Git versions side by side for testing. 
- Use this only if you need Git without touching system settings. 


On Linux (Ubuntu/Debian) 

sudo apt update 
sudo apt install git 

On Mac: 

brew install git 

Verify Installation:

git --version 

You should see something like: 

git version 2.45. 1 


Step 2 : Configure Git ( only once per computer) 
- We will Git who you are so commits have your name/email. 

git config --global user.name "Your Name"
git config --global user.email "your@email.com" 

example:

git config --global user.name "Sai Saran "
git config --global user.email "sai@example.com"

Check settings:

git config --list 

Step 3 : Create Your First Project 

1, Make a new folder for your project 

mkdir my-first-git
cd my-first-git 

2, Initialize Git in it:

git init 
-> This creates a hidden .git folder -- Git starts tracking this project.

You'll see:
Initialized empty Git repository in /path/to/my-first-git/.git/

Step 4: Add a File 

-Let's make a file:
    echo "Hello Git!" > hello.txt 
	
-check status:
    git status 
    -> you'll see 
    untraced files:
        hello.txt 
    -> Meaning: Git sees a new file but isn't tracking it yet.

Step 5: Stage the File 

git add hello.txt 

Check again:
git status 
-> Now you'll see:
   changes to be committed:
       new file: hello.txt 
-> Meaning: The file is staged, ready to be saved in history.

Step 6 : Commit (Save Snapshot)

git commit -m "First commit: added hello.txt"
Output:
- [ main (root-commit) abc1234] First commit: added hello.txt 
  1 file changed, 1 insertion(+)
  create mode 100644 hello.txt 
- This creates your first snapshot in Git's history.

Step 7: See History 

git log 
- You'll see something like:
  commit abc123456789...
  Author: Sai Saran<sai@example.com>
  Date: Tue Aug 19 20:00 2025
     First commit: added hello.txt 
- This shows commit history(yours has just 1 commit so far).

Step 8: Make a change 

Edit the file:
echo "This is my second line." >> hello.txt  

Check Status:
git status
Output:
modified: hello.txt 

Stage it:
git add hello.txt 

Commit it:
git commit -m "Added second line to hello.txt"

Step 9: See changes

check history again:
git log --oneline 

You'll see:
def5679 Added second line to hello.txt
abc1234 first commit: added hello.txt 
- You now have 2 commits ( 2 snapshots of your project)

--> Up to here, everything is local only (just on your computer).
Next step would be GitHub connection so you can push and share.

Step 10: Create a Github Repository 

step 10.1 - Go to GitHub 
1, Open your browser and go to http://github.com 
2, Log in (or create an account if you don't have one)

Step 10.2 - Create a new repository
1, On the top-right, click "+" -> New repository.
2, Enter a name,e.g., my_first_git 
3, Leave "Public" selected.
4, Don't check Add README (since we already have files locally)
5, click Create repository 

git remote add origin https://github.com/YourName/my-first-git.git

Step 11 : Connect your local repo to GitHub 

Step 11.1 : Back to your Git Bash or terminal.
Make sure you're inside your project folder.
cd my-first-git 

Now link your local repo to the GitHub one:
git remote add origin https://github.com/YourName/my-first-git.git 
- "origin" is just the nickname for your GitHub remote.
Set your main branch name (if not already "main"):

Step 12: Push (Upload) Your Work to GitHub 
- This is where you local commits go online:

git push -u origin main 
- push -> upload 
- -u -> remember this connection (so next time you can just type git push)

- Paste your personal access token instead of password (if it asks)

Step 13: Verify on GitHub 
1, Go back to your browser.
2, Refresh your repository page.
3, You'll see your file hello.txt and commit history visiable online.

Step 16: Understand what a Branch is (in Human Words)
Think of branches like:
- Main branch (main) - clean, stable code.
- Feature branch -> you playground to work on new features.
- when you're done,you merge the feature branch back into main.

Real-world example:
- You want to add a login button.
- Instead of changing files directly on main, you create a branch.
main + stable code 
new-login-feature + your work here 
When finished, you merge the branch into main 


step 17: check your Current Branch 

In your project folder:
git branch 
You'll see 
* main 
the * means you're on that branch.

Step 18: createa a new branch 
Let's create a branch where we'll add a new feature.
git branch new-feature 
Check again:
git branch 
You'll see 
main
* new features 

Step 19: Switch to the New Branch 

Tell Git:"I want to work on that branch"
Use either command:
git switch new-feature
OR
git checkout new-feature 
Your terminal will now show you're on:
(new-feature)

Meaning: Any edits you do now stay in the new-feature branch only and don't touch main.

Step 20: Make a change in the Branch 
Let's add a new line:
echo "This line is part of the NEW FEATURE" >> hello.txt 
check status:
git status 
You'll see:
modified:hello.txt 

Step 21: Commit This Work (But ONLY in this Branch)
1, Stage it 
git add hello.txt 
2, Commit it:
git commit -m "Added new feature line"
3, Check history:
git log --online 
You now have a commit on the new-feature branch.

Step 22: Switch Back to Main 
git switch main
Open the file:
cat hello.txt 
You'll notic:
The feature line in NOT there:
Because the work lives only in the new-feature branch - This the power of branching.

Step 23: Merget the Branch Into Main 
Now that you feature is complete, merge it into main.
git merge new-feature 

If everything goes well,you'll see:
update:abc128..def456
Fast-forward 
hello.txt | 1+ 
Now open the file again:
cat hello.txt 
- Now the new line is included in main.

Step 24: Delete the feature branch
- After merging, the branch isn't needed.
git branch -d new-feature 
Git will say:
Deleted branch new-feature 
This keeps your repo-clean 

Step 25; Push the Updated Main Branch to GitHub 
git push 
And because you merged:
GitHub will now include the new line too. 

Step 26: (Bonus) Push a Branch to GitHub 
Real-World: sometimes you want the branch online too.
Let's recreate and push a branch:

git checkout -b new-ui 
echo "New UI work" >> hello.txt 
git add ui.txt

git push -u origin new-ui 

Now GitHub will show 2 branches:
- main 
- new-ui 
This is how companies do Pull requests (PRs)

What is a merge conflict?
- A merge conflict happens when git does not know which version of a file to keep.
- This occurs when:
  - Two branches changed the same lines in the same file.
  - Or one branch deleted something the other modified.
  - Or both added content to the exact same place.

- Git tries automatic merging, but if changes clash, it stops and asks you.

Step 1: Setup a conflict scenario.
Let's use your existing repository.
Start on main:
git switch main 

Open your file:
echo "Line from MAIN" >> conflict.txt 
git add conflict.txt 
git commit -m "Main adds a line"

Now create a brach:

git checkout -b feature-branch 
Modify the SAME file, SAME location:

echo "Line from FEATURE brach" >> conflict.txt 
git add conflict.txt 
git commit -m "Feature adds a line"

Now Switch back to main:
git switch main 

Make Another change in main:
echo "Another line from MAIN" >> conflict.txt 
git add conflict.txt 
git commit -m "Main adds another line"

Step 2: Merge the feature branch into main 
Now the conflict occurs:
git merge feature-branch 

Git will say something like:
Auto merging conflict.txt 
CONFLICT (content): Merge conflict in conflict.txt 
Automatic merge failed; fix conflicts and then commit the result. 

This is GOOD - We triggered the conflict.

Step 3: Understand what a conflict looks like in the file.
Open conflict.txt 
cat conflict.txt 

We will see this structure:
<<<<<<< HEAD 
Line from MAIN 
Another line from MAIN 
=================
Line from FEATURE BRANCH 
>>>>>>>>> feature branch 

Let's break this down spoon-fed:
<<<<<< HEAD 
Everything under this is the verion from MAIN.
======
Divider.
Above = main version 
Below = feature branch version 
>>>>>>>> feature-branch 

This marks the end of feature branch changes.
So git is literally saying:
Here is main's version:
Here is feature branch's version.
you decide which one to keep.

Step 4: Resolve the conflict 
You manually edit the file to what you want. 
For example, if you want to keep BOTH:
The key point: Delete the conflict markers:
<<<<<<< HEAD 
============
>>>>>>> feature-branch 

Step 5: After fixing, stage the file.
git add conflict.txt 

Step 6: Complete the merge 
git commit 
Git will auto-generate a commit message like:
Merge branch 'feature-branch' 
Now the merge is complete.

Step 7: Push to GitHub 
git push
